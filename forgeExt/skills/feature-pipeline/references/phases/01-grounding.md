## 4. Фаза 1 — Инвентарь

Эта фаза **не LLM-работа**. Она снимает машинный срез того, что в коде есть на самом деле:
модули, классы по слоям, entity, эндпойнты, топики, таблицы, каталог переиспользования.
Единственный потребитель — детерминированные гейты, которым нужен список настоящих имён,
чтобы поймать выдуманное (`check_taskplan` сверяет по нему `reuses` и модули,
`check_architecture` — граф модулей). Субагент здесь не нужен: скрипт справляется за секунды.

```bash
python3 <project>/.gigacode/skills/system-analyst/scripts/ensure_inventory.py --root "<project>"
```

- **exit 0** — инвентарь готов (`ground/inventory/`). Идемпотентно: если код не менялся,
  повторный вызов ничего не делает; изменился состав или содержимое файлов — пересканирует сам.
- **exit 2** — инвентарь пуст (0 модулей и 0 entities). Это НЕ «маленький проект», это
  «сканировали не тот корень» либо «сканировать нечего». СТОП: уточни корень репо кода
  у пользователя, не закрывай шаг.

> **Почему он эфемерный.** `ground/inventory/` в git не едет — каталог самоигнорирующийся.
> Инвентарь производен от кода и снимается заново, поэтому его не нужно ни коммитить, ни
> «поддерживать в свежести». Раньше он лежал закоммиченным в `docs/system-analysis/`, и это
> давало конфликт на каждый merge (файл переписывался целиком на каждой фиче), дрейф
> относительно кода и абсолютные пути машины в общем спек-репо.

**Архитектурный граунд модулей (эмитни здесь — дёшево, идемпотентно).** Граф межмодульных
зависимостей (что проект УЖЕ соединяет; сканирует и `build.gradle`, и `pom.xml`) — его
использует гейт бриф `05-verify.md` §8.3c, чтобы отличать принятые связки от новых
арх-связываний:
```bash
python3 <project>/.gigacode/skills/feature-pipeline/scripts/check_architecture.py \
    --root "<project>" --emit-ground
```
`--emit-ground` без пути пишет `architecture-ground.json` в `ground/inventory/`. Файл
курируемый: архитектор может уточнить правила в `ground/architecture-policy.json`
(`module_deps.forbidden`/`allowed_new`).

**Человеческий обзор системы — отдельно и не здесь.** MD с диаграммами (`system-analyst`,
`docs/system-analysis/`) — документация для людей, а не топливо гейтов. Пайплайн её не
требует и не обновляет; пользователь зовёт `system-analyst` сам, когда она нужна.

> **ХАРД-ГЕЙТ закрытия (детерминированный, в `update.py`).** Шаг `01-grounding` НЕ закроется,
> пока инвентарь не содержит хотя бы один модуль ИЛИ entity (`_check_grounding_substance`).
> Пустой инвентарь = гейты дизайна останутся без топлива и выродятся в warning «кросс-чек
> пропущен» — узнаешь об этом слишком поздно. Пропуск только через
> `override_judge --judge grounding-substance-01-grounding` после явного «да» пользователя
> (§0.6.1) — и лишь когда инвентарь объективно недоступен.

Закрой шаг явной командой:
```bash
python3 <project>/.gigacode/skills/pipeline-state/scripts/update.py \
    --skill feature-pipeline --feature <slug> --step-id 01-grounding --status completed
```
