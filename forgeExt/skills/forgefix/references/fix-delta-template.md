# Шаблон дельты фикса (`sdd.md` на шаге `fix-spec`)

Дельта фикса — **не SDD фичи**. Полный шаблон (`sdd/references/sdd-template.md`: ДКБ, модель
угроз, API-контракты, модель данных) здесь не нужен и его гейт (`check_sdd_doc.py`) не
применяется: у фикса другой гейт — `forgefix/scripts/check_fix_delta.py`.

Задача дельты одна: **точечно поправить те требования мастера, которые баг показал неверными
или неполными.** Отсюда три правила.

## Правило 1. Название требования — дословно из мастера

`/forge-spec merge` сопоставляет требования по нормализованному названию:

| В дельте | В мастере | Операция merge |
|---|---|---|
| `### Создание заявки` | `### REQ-0007: Создание заявки` | `~ modify` — правка на месте, ID сохраняется |
| `### Валидация email заявки` | нет такого | `+ add` — заведётся НОВОЕ требование |

Какое именно требование чинит баг, ищет не глаз, а `forgefix/scripts/find_spec_anchor.py` — по
провенансу `[from: <стори>]` в мастере, старым `task-plan.json` (какая стори заводила изменённые
файлы) и связям Jira. Его результат фиксируется решением `sources.spec_anchor` (ID требования либо
`none`), и гейт дельты сверяет, что правишь именно его.

Поэтому перед записью открой мастер по ID якоря и **скопируй название требования дословно, без
ID-префикса**. Новое требование заводи, только когда якорь = `none`: баг вскрыл поведение,
которого в спеке действительно нет.

## Правило 2. Требование переносится ЦЕЛИКОМ, правка — внутри него

`modify` заменяет блок требования в мастере полностью. Если в дельте оставить один новый
сценарий, остальные сценарии требования **будут потеряны**. Поэтому: скопируй блок требования
из мастера (утверждение + все его сценарии), внеси точечную правку и добавь регресс-сценарий
бага. Гейт это форсит — при уменьшении числа сценариев он валит шаг.

## Правило 3. Дельта минимальна

Лимиты гейта: не больше **3** требований и **160** строк. Больше — это переписанная спека, а не
фикс; вынеси лишнее.

---

## Скелет

```markdown
# SDD: <кратко — что чинили>

## 1. Назначение и результат
<1–2 строки: какое поведение было сломано и каким оно должно быть. Без «как чинили».>

## 3. Функциональные требования (Given-When-Then)

### <Название требования — ДОСЛОВНО из мастера>
<Утверждение требования из мастера с внесённой точечной правкой.>
- **Given** <существующий сценарий мастера> **When** … **Then** …
- **Given** <существующий сценарий мастера> **When** … **Then** …
- **Given** <условие бага> **When** <действие> **Then** <корректное поведение>   ← регресс-сценарий
```

Регресс-сценарий обязателен: баг — это сценарий, который спека не описывала (или описывала
неверно), и после фикса он должен быть в ней зафиксирован. Он же должен совпадать с тестом,
написанным на шаге `fix-red`.

## Чего в дельте быть не должно

- Кода: ```` ```java/sql/xml/diff ````, `import …;`, `@RestController`, `public class` — спека
  описывает поведение, а не реализацию (гейт валит).
- Разделов, которых фикс не касается (архитектура, threat model, NFR): их место — мастер, и они
  не менялись.
- Описания самого фикса («добавили guard clause») — это `fix-plan.md` и код, не спека.
