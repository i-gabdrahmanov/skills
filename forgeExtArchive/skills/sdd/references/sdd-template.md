# SDD — Specification-Driven Development документ (PDLC v3.5)

В v3.5 **спецификация первична, код производен** (стр. 66). SDD-документ устроен так, чтобы агент
получил его и реализовал задачу **без дополнительных вопросов**. Скилл `sdd` генерирует `sdd.md`
из идеи/Jira (и BRD, если бизнес-анализ включён) рядом с будущим `tech-design.md` в папке фичи.
Tech-design затем проектирует ПО `sdd.md` и проставляет `sdd_ref` в каждую задачу task-plan.

`sdd.md` — это **дельта-спецификация** (спека одного изменения) по обязательному составу
разделов SDD-шаблона. Форматирование внутри раздела свободно, но **набор разделов и заголовки
фиксированы** — по ним гейт `check_sdd_doc.py` и tech-design находят нужное. Design (как строим)
и разбивку на задачи в спеку НЕ включаем — они живут в `tech-design.md` / `task-plan.json`
(в спеке — только ссылка на них).

## Обязательные разделы `sdd.md`

```markdown
# SDD: <фича>

**Jira:** <KEY, напр. KIDPPRB-8639 — ПЕРВОЙ строкой, если задача из Jira; иначе опусти строку>
**Spec ID:** <id изменения/репо; для дельты — имя change>
**Статус:** <draft | approved>  **Версия/аудит:** ведёт git (кто/когда/что менял)
**BRD:** ./brd.md  <опусти строку, если бизнес-анализ выключен и brd.md нет>

## 1. Назначение и результат (Purpose & Outcomes)
Зачем фича, какую проблему решает, кто пользователь, какой business outcome ожидаем.
(2–5 предложений.) Для бэковых КЭ бизнес-метрики — по применимости.

## 2. Границы охвата (Scope boundaries)
- **В рамках:** что делаем.
- **Не в рамках:** что явно НЕ делаем.
- **Отложено:** что осознанно откладываем на потом.

## 3. Функциональные требования (Given-When-Then)
По каждому сценарию — приёмочный критерий в формате:
- **Given** <предусловие> **When** <действие> **Then** <ожидаемый результат>
Покрыть и happy-path, и ошибочные ветки (null, пусто, нет прав, неверный статус).

## 4. Ограничения и допущения (Constraints & assumptions)
Точный стек («React 18 + TS + Vite», не «React»), NFR (производительность, нагрузка,
идемпотентность, лимиты, SLA), регуляторные/законодательные ограничения — ссылкой или явно.
Неприменимое помечай «не применимо».

## 5. API-контракты
Для каждого нового/изменённого эндпойнта: метод, путь, request/response схема, коды ошибок,
авторизация. Для Kafka: топик, ключ, схема сообщения, направление (producer/consumer).
Если не затрагивается — «не затрагивается».

## 6. Модель данных
Затрагиваемые entity/таблицы, новые поля — на уровне «что меняется». БЕЗ Liquibase-changeset,
имён классов и пакетов: реализационные детали миграций — забота фазы tech-design.

## 7. Критерии приёмки (Acceptance & verification)
Сводный чек-лист «сделано» — каждый пункт проверяемое утверждение Given-When-Then, на него
сошлётся задача task-plan через `sdd_ref`. Какие тесты/conformance подтверждают.

## 8. Архитектурный контекст (Architectural context)
Где фича живёт в ландшафте, зависимости, shared services. **Границы доверия:** сетевое
размещение взаимодействующих компонент (секторы сети); фронтальные/шлюзовые/интеграционные/
бэковые компоненты; компоненты на неуправляемых банком устройствах (МП клиента). Детальный
data flow, трассируемый к этому разделу. Если для КЭ неприменимо — «не применимо: <причина>».

## 9. Модель угроз и безопасность (Security & threat model)
Перечень обрабатываемых данных и их классификация; threat surface; частная модель угроз;
каналы взаимодействия и протоколы. Если неприменимо — «не применимо: <причина>».

## 10. Пользовательские истории и привилегированные сценарии
User Story («Как <роль>, я хочу … чтобы …»); роли/типы пользователей и изменения ролевой
модели. **Привилегированные сценарии** (администрирование, КВР, подтверждение, АСП) — выделить
отдельно, с требованиями к логированию и аудиту. Для бэка/техсервисов — техсценарии.

## 11. Принятые решения (Prior decisions)
Уже принятые архитектурные решения, влияющие на реализацию: БД, библиотеки, ключевые выборы
и их обоснование (со ссылкой на источник решения, если есть).

## 12. Регуляторные требования (Regulatory & compliance)
Ссылки на нормативку, требования аудита/комплаенса. Только для клиентских/регулируемых КЭ;
для внутренних инструментов — «не применимо: <причина>».

## Риски и допущения
Что может пойти не так, какие предположения сделаны.

## Реализация и задачи
Раскладку по слоям (Design) и разбивку на задачи см. в `./tech-design.md` и `./task-plan.json`
— в спеке НЕ дублируются (спека = ЧТО, tech-design = КАК).
```

## Якоря для трассировки

Размечай разделы так, чтобы tech-design мог сослаться на них из `sdd_ref` задачи
(например `docs/feature-pipeline/<slug>/sdd.md#t1` или якорь на конкретный сценарий §3/§7).
Каждой будущей задаче должен соответствовать ≥1 пункт Given-When-Then из §3/§7 — это даёт
прямую трассировку требование → задача → тест → evidence.

## Состав, «по применимости» и строгость гейта

Обязателен именно **состав разделов**, а не конкретный формат внутри них. Часть разделов может
не применяться к конкретной КЭ — тогда оставь заголовок и явно напиши **«не применимо: <причина>»**
(осознанно закрыть раздел, а не молча выпустить). Насколько жёстко гейт требует разделы ДКБ
(§8 Архитектурный контекст, §9 Модель угроз, §12 Регуляторка и §10/§11) — задаётся в
`ground/pipeline.json` ключом **`sdd.security_gate`**:

- `hard` — все разделы обязательны с контентом (регуляторка/§8/§9 — допускают «не применимо: причина»);
- `applicability` (дефолт) — §8 Архитектурный контекст и §9 Модель угроз обязательны (контент
  или «не применимо: причина»); §10/§11/§12 — предупреждение, если отсутствуют;
- `soft` — новые разделы (§8–§12) только предупреждают; жёстким остаётся ядро (§1–§7 + GWT).

## Зачем строго

Строгий SDD = меньше «додумывания» агентом, выше autonomy-уровень, и прямая трассировка
требование → задача → тест → evidence. Это ядро Intent Loop (стр. 59). Гейт `check_sdd_doc.py`
проверяет наличие `sdd.md`, обязательных секций (по политике `sdd.security_gate`) и хотя бы
одного сценария Given-When-Then; без этого фаза `02-sdd` не закрывается. Гейт также **ВАЛИТ** при
наличии код-блоков (```` ```java/kotlin/sql/diff/xml ````) или сигнатур кода
(`import …;`, `@RestController`/`@Service`/`@Entity`, `public class/interface/enum`) —
SDD не содержит реализацию; Liquibase-фрагмент даёт лишь предупреждение.
