description: "Архив доков готовых строек: status | put <slug> | abandon <feature> | list | restore <slug>. Обычно срабатывает само на /forge-merge."
---
Убирает ЗАВЕРШЁННУЮ фичу с рабочего стола обеими половинами: доки
`docs/feature-pipeline/<слаг>` → `docs/archive/<слаг>` (путь сохраняется, у фикса —
`<стори>/fixes/<баг>`), стейт прогона `ground/statements/<skill>/<feature>` →
`ground/archive/<skill>/<feature>`, git-чекпойнты фичи удаляются. Стори уносит свои
`fixes/` целиком — вместе со стейтами их прогонов (restore возвращает их обратно); фикс с
несведённой дельтой стори не отпускает. Скрипт сам разбирает
подкоманду и аргументы, тебе парсить их не нужно.

Выполни в корне проекта:

```bash
python3 .gigacode/skills/pipeline-state/scripts/archive.py --project . {{args}}
```

Если аргумент пуст — выполни `status`.

Дальше:
- Покажи вывод скрипта пользователю **как есть**, не пересказывая своими словами.
- Слаг сам не угадывай: `status` показывает, что готово к архивации. Дельту фикса зовут ключом
  бага (`put BUG-512`), хотя лежит она внутри стори — скрипт принимает короткое имя, пока оно
  однозначно, и сам просит полный слаг при совпадении в нескольких стори.
- Обычно архивация происходит сама, по успеху `/forge-merge`. Эта команда нужна, когда у фичи
  нет дельты (мастер выключен, фикс без правки спеки), когда архивируют задним числом или
  когда нужен `restore`.
- Код exit 3 — не ошибка, а «нужно решение»: слаг неоднозначен, фича есть в нескольких
  namespace, либо для `abandon` / `put --force` нет согласия пользователя. Покажи варианты
  и спроси, сам не выбирай.
- Код exit 2 — отказ гейта (`[archive] DENY: …`): стройка не завершена, внутри идёт живой
  прогон, дельта (своя или фикса внутри стори) не сведена с мастером, либо формат мастера не разобран (состояние дельты
  неизвестно — тогда веди на `/forge-spec research`). Покажи причину и остановись — гейт
  снимается только явным `--force --reason '<почему>'` по просьбе пользователя, сам его не
  подставляй. `put --force` — R4: прежде чем запускать, зафиксируй его согласие
  `record_approval.py --key archive-force-<слаг> --approved-by user --reason "<почему>"
  --evidence "<дословная фраза пользователя>"`. Без маркера скрипт ответит exit 3.
- `restore` возвращает доки и стейт, но НЕ git-чекпойнты завершённой стройки — `put` их
  удаляет. Если пользователь может захотеть откат (`rollback.py`), скажи это до архивации.
  Брошенный прогон (`abandon`) `restore <feature>` возвращает целиком, с чекпойнтами.
- Заархивированный прогон перестаёт считаться активным: он выпадает из резолверов
  `ground/statements/*/*/`. Это и есть цель, а не побочный эффект.
- `abandon <feature> --skill <S> --reason "<почему>"` — для прогона, который БРОШЕН и доков не
  успел дать. `put` на него не работает (нет каталога доков — проверка не снимается `--force`),
  а руками из `ground/statements/` удалять нельзя: это control-plane, `state-write-guard` режет
  unlink. Стейт переезжает в `ground/archive/`, причина пишется в `archive-meta.json`.
  `status` показывает такие прогоны отдельным блоком «Стейт без доков».
  Сам не решай, какой прогон брошен: в списке может быть и тот, что идёт прямо сейчас.
  Покажи блок пользователю и спроси, какой снимать. `abandon` — R4 (прогон перестаёт
  числиться живым; вернуть — `restore <feature>`): по его ответу зафиксируй согласие `record_approval.py --key
  abandon-<feature> --approved-by user --reason "<почему брошен>" --evidence "<дословная фраза
  пользователя>"`, затем запусти abandon. Без маркера — exit 3, ничего не изменится.
- Ничего не коммить и не пушить: forge пишет только в рабочее дерево, коммит делает пользователь.
