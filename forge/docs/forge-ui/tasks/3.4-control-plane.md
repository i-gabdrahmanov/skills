# 3.4 — Обобщения общего control-plane под фронт

**Этап:** 3 · **Зависит от:** — · **Статус:** todo
**Спека:** INV A11, F9, F14, D3 · **QG:** N7, N11

## Зачем
Общие хуки forge написаны под Java: `.daiver/` никто не защищает, `pii-boundary` блокирует
реалистичные мок-данные из макета, фронтовый прод-код пишется как R1, сборки npm/tsc не видны
ролям SoD.

## Что сделать
- **state-write-guard:** `.daiver/config.yaml`, `component-map.yaml`,
  `design-system-requirements*.json`, `tracks/*/track.yaml`, `**/build-state.json`,
  `**/verify-state.json`, `run.json`, `plan.json`, `plan.lock.json`, `resolutions.json`,
  `*.canonical.json`, `visual-requirements.*`, `verify/**`, `versions/**`, `baseline/**` — прямая
  запись и rm/mv моделью запрещены (пишет только движок своим процессом).
- **pii-boundary:** PII-подобные строки в `<outputDir>/**/mocks.ts` и `__mocks__/` пропускаются,
  только если каждая дословно есть в текстах канона активного трека (хелпер движка
  `daiver.texts.mockup_texts`); иначе — как сейчас.
- **risk-policy `path_risk`:** фронтовый прод-код `.tsx/.jsx/.vue/.svelte` (не тесты) → R2
  (нужен закрытый design-шаг); тесты `*.spec.ts`, `*.test.tsx`, `*.e2e.spec.ts` → R1; согласовать
  с `_project.is_test_path`.
- **`BUILD_CMD_RE`** в sod-enforcer и inline-phase-guard (обе копии, пин теста):
  `npm|pnpm|yarn|npx … build|test|run|exec`, `tsc`, `vite`, `playwright`.
- **inline-phase-guard:** продуктивные MCP-инструменты шага — новое поле реестра `phase_tools`
  (`daiver_pixso_pull`/`daiver_normalize`/`daiver_resolve_*`/`daiver_plan_write` → ui-design;
  `daiver_build_state_set` → ui-build; `daiver_screenshot`/`daiver_verify_*` → ui-verify): главный
  агент не исполняет фазу инлайн.

## Готово, когда
- Тесты каждого хука на новые случаи и пины копий `BUILD_CMD_RE`; `test_branches_registry` видит
  `phase_tools`; evals N7 (append карты без согласия), N11 (config руками); бэковые сценарии хуков
  не изменились (весь `run-hook-tests.sh` зелёный).

*Заметка (2.6).* Файлы, которые пишет только движок и которые охраняет `state-write-guard`, пополняются: `plan.md`, `ui-plan.md`, `resolution-report.md` (рядом с `plan.json`
и `plan.lock.json`). Правка руками уже ловится движком (план `stale`, подпись `stale`), но запись надо запретить, а не обнаруживать. `phase_tools` шага `ui-design`: + `daiver_plan_contract`
(он ПИШЕТ `ui-plan.md`/`plan.lock.json` и снимает устаревшее согласие `ui-plan-<KEY>` через `revoke_approval`).

*Заметка (3.1).* `phase_tools` шага `ui-build`: ОБА инструмента — `daiver_build_state` (создаёт и пересверяет файл) и `daiver_build_state_set`, а не только `_set`. Замок состояния — `ground/build-state.lock` (файл control-plane, как
`resolve.lock`), его `state-write-guard` трогать не должен; охраняется `**/build-state.json` (пишет только движок: правка руками обнаруживается движком как повреждение, но запрет должен быть до записи).

*Заметка (3.2).* `phase_tools` шага `ui-build`: продуктивные — `daiver_build_state`, `daiver_build_state_set` и `daiver_svg_assets` (с `moduleDir` копирует svg в модуль); читающие (`daiver_section`, `daiver_color_tokens`,
`daiver_ds_*`, `daiver_map_lookup`, `daiver_spec`) в `phase_tools` не нужны. Субагент `ui-build` чинит красный билд сам и запускает `npm run build` / `npx tsc` руками — `BUILD_CMD_RE` роли dev должен их пропускать. Гейт ждёт
`buildCommand` до 900 с (`ui_gate.py build --timeout`), раннер `record_gate.py` — до 1800 с: таймаут раннера выше таймаута команды, чтобы отказ с хвостом вывода успевал напечататься. `build-state.json` теперь может нести
`noCode: true` у секций без кода — запись руками по-прежнему запрещена. Важно для безопасности: гейт исполняет `project.buildCommand` из `.daiver/config.yaml` процессом Python — в обход Bash-хуков
(`destructive-blocker`, `sod-enforcer` этот процесс не видят), поэтому пока `state-write-guard` не закрыл `config.yaml` (первый пункт этой задачи), правка конфига моделью равна выполнению произвольной команды гейтом.
