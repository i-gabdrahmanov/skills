# 3.2 — Шаг ui-build: пролог, правила сборки, гейт

**Этап:** 3 · **Зависит от:** 2.6, 3.1 · **Статус:** done
**Спека:** §13.1, §13.2, §13.5 (правила 1–14), §11.3, §13.8 · **INV:** A9, B9, B17, B18, C11–C17, C20,
C39, F4, F5, F8, F18 · **QG:** P1 (часть)

## Зачем
Сборка экрана строго по подписанному плану и измеренным значениям макета, в стиле проекта, с
проверяемым итогом (сборка проекта зелёная).

## Что сделать
- Бриф `ui-build` (субагент, роль dev):
  - Пролог ОДИН раз на трек: прочитать каждый файл `project.conventions` (они сильнее примеров
    forge-ui); карта цветов; пустой `mocks.ts`. Для page-изменений пролога нет (6.4).
  - Цикл: `daiver_build_state` → по `next`: `set in_progress` → `daiver_section` → строить ТОЛЬКО
    это поддерево → `set done` с outputs и hash; дальше — следующий кадр (6.1).
  - Правила: стек из конфига; local-композиция из анатомии, library-инстанс — чёрный ящик с
    content; пропсы сверены с источником библиотеки (дефолты не передавать, набор не расширять);
    импорты — дословно из карты/ds_lookup, иконки — из своего пакета; иконка — только компонент
    библиотеки, иначе `icons.fallback`; арт — `daiver_svg_assets(moduleDir)`, нет файла —
    плейсхолдер; раскладка 1:1 (direction/gap/padding/align/wrap, fill/hug/px, box → absolute);
    корневой px-размер кадра не хардкодится, внутренние px — точно; цвета → переменные только по
    ТОЧНОМУ значению; local-компоненты → `outputDir/local/`; тексты макета → `mocks.ts` и
    defaultProps, не в разметку; семантика по `tag`; occluded не строится; спеки: States/Events/
    Validations подключают логику, «Данные» решают типизацию (пути из спеки, иначе моки и
    `onX`-пропсы, `// TODO(forge-ui): wire business logic`).
- Движок: **`daiver_color_tokens()`** (дополнение к спеке — арифметика в коде, INV-A1): разбор
  `styling.colorsFile` (less/scss/css-переменные) → карта «точное значение → переменная»
  (нормализация регистра и короткого hex); близкий цвет не угадывается.
- `ui_gate.py build`: все секции done, stale нет, outputs существуют, затем `project.buildCommand`
  (таймаут, хвост вывода в ответе); не компилируется — субагент чинит сам (§13.8), гейт красный.

## Готово, когда
- Бриф обновлён; `test_color_tokens.py` (точное совпадение, нормализация hex, нет совпадения →
  None); `test_ui_gate_build.py` (заглушка buildCommand: зелёная/красная, stale-секция → не готово).

*Заметка (2.6).* Решения по узлам секции сборка берёт из `plan.json` → `sections[id].nodes[]`: `{component, props}` | `{resolution: local, local?: имя}` | `{resolution: ignore}`
(узлы без записи — простая разметка по канону); оболочка над секциями — `tree` (контейнеры с дайджестом раскладки; секции в нём — ссылки `{section: id}`); раскладка: принятые hints
лежат в `layout.decisions[]` (`apply` → `hints` обязательны для сборки, `keep-px` → px остаётся, `group` → ряд/колонка из названных детей с `gap`/`gaps` и `box`, посчитанными кодом),
непринятые из канона не применять. Общие local-компоненты — `locals[]` (`shared: true`, `creator` — секция, которая создаёт файл в `outputDir/local/`). Токены/цвета без токена — `design`.
Сверку цветов с `project.styling.colorsFile` план НЕ делает — это `daiver_color_tokens` этой задачи. Бриф `ui-build` не должен называть `daiver_plan_sign` (его нет) и обязан
сверять `weightBudget` плана с аргументом `daiver_section`.

*Заметка (3.1).* Цикл — инструменты `daiver_build_state` / `daiver_build_state_set` (`daiver/build_state.py`, формат и правила — в докстринге модуля). `next` — объект `{sectionId, name, status, outputs?}` (у stale `outputs` — файлы
прежней сборки: правка на месте), `weightBudget` ответа — бюджет для `daiver_section`, `nextStep` уже несёт готовый вызов. Переходы держит код: `done` только из `in_progress`, `in_progress` только для `next`, `done` требует `outputs`
(пути от корня проекта; голое имя файла, `..`, каталог — отказ; несуществующий путь — `warnings`, они повторяются в каждом `daiver_build_state`) и `hash` — `section.hash` из `daiver_section`; чужой hash — отказ, настоящий в отказах
не называется (бриф не должен советовать «возьми hash из ошибки»). `ui_gate.py build` берёт готовый читатель `build_state.gate_problems(root, track, frame)` (нет состояния / не сверено с планом / секции не done / outputs не на диске;
план против макета — отказом с лечением) и добавляет `buildCommand`; в `ui_gate.py` он пока не подключён. Секция, чей корень решён `ignore`, ничего не строит, а `outputs` обязателен — тупик, решить по боевому плану.

## Результат
Четыре части. **(1) Бриф** — `skills/forgeui/SKILL.md` §4 (≈50 строк): пять нумерованных пунктов (статус и `daiver_build_state` → пролог → цикл секции → 14 правил сборки → гейт через раннер), JSON субагента
`completed | failed | needs_input`, абзац оркестратора; в §1 и §3.1 убраны слова «сборки в движке нет»; `FORGE.md` — состояние ветки. **(2) Движок цветов** — `daiver/color_tokens.py` и инструмент
**`daiver_color_tokens(track?, frame?)`** (в `EXPECTED_TOOLS`). **(3) Гейт** — `daiver/build_gate.py` и `ui_gate.py build [--timeout]` (exit 0 / 1 / 2; `verify` по-прежнему 3). **(4) Тупик «секция без
кода»** из 3.1 закрыт кодом (ниже). Тесты: `test_color_tokens.py` (43), `test_ui_gate_build.py` (34), `test_ui_build_brief.py` (19), `test_build_state.py` 95 → 111; правки пинов — `test_ui_design_brief.py`
(лимит файла 320 → 345 строк, живой текст теперь до §5), `test_plan_contract.py`, `test_resolution_report.py` (`build` больше не «не реализован»), `hooks/test_daiver_mcp.py`. Мутационно проверено 38 правил (одноразовый
скрипт: копия дерева, правка текста модуля): выжили 0, каждый мутант убит настоящим падением теста, а не ошибкой импорта.

- **Данные образца («Modal»).** Цвета экрана — четыре: `rgba(255, 255, 255, 1)` (фон корня), `rgba(31, 20, 51, 0.12)` (обводка корня) и два слоя тени одной строкой `box-shadow` — `rgba(11, 11, 30, 0.161)`,
  `rgba(11, 11, 30, 0.039)`; три инстанса несут цвета только в `component.content[].color` (цвета библиотечных компонентов — в список экрана не входят). `design.rawColors` плана (2.6) даёт два (фон и обводка, без теней и
  без токенов) — это разные определения, не расхождение. Ответ `daiver_color_tokens(track)` на «Modal» — 17 строк `indent=1`, `daiver_build_state` — 15 (+`planMd`); полный цикл (pull → резолв → план → состояние →
  секция → done → `ui_gate.py build` с заглушкой) зелёный.
- **Цвета (INV-B18, A1).** Файл `project.styling.colorsFile` разбирает код: `@x` (less), `$x` (scss, флаги `!default`/`!global`), `--x` (css); значения — `#rgb/#rgba/#rrggbb/#rrggbbaa` в любом регистре, `rgb()/rgba()`
  через запятые или пробелы (+ `/ альфа` числом или процентом), `white/black/transparent`, алиасы цепочкой (≤ 16 переходов, круги, а не рекурсия — итог не зависит от порядка объявлений); всё приводится к виду канона
  `rgba(R, G, B, A)` (`canon.fmt_rgba`, альфа до 3 знаков). Совпадение ТОЧНОЕ: ни допуска по каналу, ни по альфе (0.121 ≠ 0.12 — тест). Переменная с разными значениями (тема, переопределение) в карту не входит
  (`conflicts`); у значения несколько переменных — первая по файлу, литерал раньше алиаса (`ambiguous` называет число). Цвета экрана берёт сам код из канона: фон, градиент, цвет обводки, цвета ВНУТРИ строки тени, цвет
  текста — узлов, которые рисует сборка (без occluded и без библиотечных чёрных ящиков). Ответ: `matched` («цвет → переменная»), `raw`, `conflicts`, `skipped`, `ambiguous`; без `track` — карта файла (40 строк и счётчик
  остатка). Нет `colorsFile` или формат вне .less / .scss / .css — все цвета сырые, без ошибки; файла нет, путь вне репо, не UTF-8, больше 2 МБ — отказ с лечением. Инструмент только читает.
- **Тупик секции без кода (из 3.1).** Секция, чей КОРЕНЬ в плане решён `ignore` (узел не строится вовсе, §5.2), закрывается самой сверкой `daiver_build_state`: `done` + `noCode: true`, без `outputs`, без вызова модели
  (признак читает `plan.no_code_sections` из `sections[].nodes`; формат плана не менялся, замок и подпись не затронуты). `next` её не называет, `progress` считает готовой, ответ перечисляет `noCode: [id…]`, `daiver_build_state_set`
  отказывает («без кода… движок закрыл её сам»), гейт сборки и лестница 1.10 видят `done` (`test_status_ladder` как был). Перемена решения видна: ignore → строить — секция снова `pending` (в `added`; хеш секции от вердикта
  не зависит, по хешу перемену не увидеть), собрана → ignore — файлы остаются на диске, предупреждение один раз в вызове, который записал перемену. Все секции кадра без кода — отказ, как при пустом `buildOrder`. Выход выбран
  так (а не «`done` без outputs по вызову модели»), потому что хеш-доказательство «ты смотрел секцию» здесь не нужно, а лишний вызов слабой модели — лишний риск. Файл состояния расширен ключом `noCode` совместимо: лестница читает
  только `status`.
- **Гейт.** Порядок: кадры трека (каждый: `build_state.gate_problems` — состояние есть и сверено с планом, ничего не pending / in_progress / stale, `outputs` на диске) → `project.buildCommand` задан → только тогда команда
  запускается: из корня репо, строкой оболочки (`a && b`), stdin закрыт, вывод во временный файл (в память — только хвост), таймаут 900 с (`--timeout`; раннер `record_gate` ждёт 1800 с); по таймауту на POSIX убивается вся группа
  процессов. Красный итог (код ≠ 0, таймаут, не запустилась) — exit 1 и хвост (последние 40 строк / 3000 знаков, без ANSI и «\r») последним в stderr — раннер берёт конец вывода; зелёный — exit 0. Гейт сам ничего не пишет.
  Подпись плана здесь не перепроверяется (ui-guard, 3.3).
- **Бриф.** Решения по узлам модель берёт из `plan.md` кадра, а не из `plan.json` (путь называет `daiver_build_state` → `planMd`): тот же план в сжатом виде, узлы одной группы свёрнуты в «×N»; для сборки в строку групп раскладки добавлен
  `box=x,y,w,h` (раньше его не было). Бюджет `daiver_section` — только из ответа `daiver_build_state` (бюджет плана). Пролог выполняется в каждом запуске субагента (контекст пуст), а файлы создаёт только первый (`mocks.ts`).
  Лимит длины: SKILL.md 294 → 339 строк, §4 пинится на ≤ 52 (`test_ui_build_brief`). Бриф не называет `daiver_plan_sign`, резолв и запись плана (они на ui-design), сам не пишет согласий.
- **Решено там, где спека свободна** (README → «Отклонения»): кто собирает оболочку над секциями — ПОСЛЕДНЯЯ секция порядка плана (спека называет только секции, а `ancestors` — «куда положить»); каталог модуля —
  `<outputDir>/<имя кадра>` (конвенции важнее); пролог каждый запуск; устаревший план — статус субагента `failed` с причиной (отдельной причины `blocked` у шага нет); пределы гейта (900 с, 40 строк / 3000 знаков).
- **Граница.** Не сделано, как и просили: хук `ui-guard` (3.3), обобщения control-plane — `build_system` npm/pnpm/yarn, R2, `BUILD_CMD_RE` (3.4), правка существующей страницы без пролога (6.4), несколько кадров в один модуль (6.1: гейт
  требует состояние у КАЖДОГО кадра трека, у кадров-состояний `stateOf` — тоже, пока их не строит 6.2). Безопасность до 3.4: гейт исполняет `project.buildCommand` из `.daiver/config.yaml` процессом Python, мимо Bash-хуков, — пока
  `state-write-guard` не закрыл конфиг, его правка моделью равна запуску произвольной команды (заметка в 3.4). Заметки для 3.3, 3.4, 4.3, 4.7, 6.1, 6.4 и чек-лист шага для X.4 дописаны в их файлы.
- **Не проверено данными** (боевых сборок нет; допущения названы и в README → «Нужно от пользователя»): реальный файл цветов команды (формы записи, темы, функции, интерполяция); сколько цветов экрана находят переменную; правило «литерал
  раньше алиаса, первая по файлу»; `project.conventions` на боевом репо; как слабая модель читает `plan.md` (длина на большом экране, сопоставление строк «×N» с узлами), правило оболочки «последняя секция» и имя каталога модуля;
  встречается ли на боевом экране секция с корнем `ignore` (ignore у вложенного узла оставляет секцию с разметкой вокруг, ignore у оболочки над секциями спека не определяет); время и вывод настоящего `npm run build`/`tsc`
  (таймаут 900 с подобран, не измерен; хватает ли 40 строк для самоисправления); убийство дерева процессов проверено на POSIX, на Windows (`taskkill /T /F`) — нет; поведение гейта на кадрах-состояниях (6.2).
