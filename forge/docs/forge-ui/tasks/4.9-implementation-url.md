# 4.9 — URL реализации, dev-сервер, рецепты открытия

**Этап:** 4 · **Зависит от:** 4.2 · **Статус:** done
**Спека:** §14.2 · **INV:** D4, D6, F6, F13, C23 · **QG:** N2, N10

## Зачем
Проверять можно только ту страницу, до которой захват честно добрался: адрес не угадывается,
модалка открывается записанным рецептом, условия захвата одинаковы на всех итерациях.

## Что сделать
- Разрешение URL в `daiver_verify_state`: `frames[].url`; main → `implementation.url` трека;
  state → url своего экрана; dialog не наследует никогда. Пусто — interactive спрашивает ОДИН раз и
  пишет `daiver_track_manifest`; автономно — `blocked: no-implementation` с именем кадра.
- Dev-сервер: interactive НЕ стартует его сам никогда; автономный прогон запускает ЗАПИСАННЫЙ
  `devCommand` (данность, не догадка), ждёт URL, глушит после цикла; нет команды или не поднялся →
  `blocked: implementation-unreachable`. Хелпер `daiver/verify/devserver.py` (запуск в своей группе
  процессов, опрос готовности URL с таймаутом, гарантированное завершение) — его зовёт 7.2.
- Рецепт открытия диалога/состояния: вырабатывается ОДИН раз с человеком (триггер в исходниках
  модуля → `daiver_screenshot(actions)` → проверка картинкой (vision) или вердиктом состояния →
  `daiver_track_manifest(frame:{open})`); автономия клик не выдумывает → `blocked: no-open-recipe`.
  clip — решение агента (макет модалки — элемент, макет экрана — весь viewport); выбранные recipe,
  clip и viewport пинятся в verify-state и одинаковы во всех итерациях.

## Готово, когда
- `test_implementation_url.py`: матрица разрешения URL по ролям; devserver на команде
  `python -m http.server` — старт, ожидание, гарантированное завершение; рецепт сохраняется и
  переиспользуется; отличающийся clip/viewport на следующей итерации — отказ.

*Заметка (4.1).* `daiver/proc.py` уже даёт то, что нужно dev-серверу: `popen_group(cmd, **kw)` (процесс в своей группе), `kill_group(proc)` (SIGTERM → SIGKILL ВСЕЙ группе, лидер забран, повтор — пустая операция: номер
группы мог достаться чужому процессу), `group_alive(proc)`; Windows (`taskkill /T`) не проверен. `devserver.py` берёт их, а не пишет третий вариант (второй — `build_gate._kill_tree`, 3.2: не менялся). Браузер и dev-сервер
независимы: `launch_or_skip` не знает про сервер.

## Результат
Три части: разрешение адреса и недостающего (`verify/implementation.py`), dev-сервер (`verify/devserver.py`), пин захвата (рецепт, clip, viewport). Инструмента MCP не прибавилось: `daiver_verify_state` (4.8) теперь отдаёт `implementation {url, open, devCommand, role, need?, ask?, blocked?, supply?}` и `pinned`; `daiver_screenshot` (4.2) отказывает на отличающийся захват. Тесты: `test_implementation_url.py` (**30**: роли, режимы, dev-сервер на настоящем `python -m http.server`, рецепт и пин на настоящем треке).

- **Адрес** — `track.implementation_url` без изменений (экран → `frames[].url`; первичный → `implementation.url` трека; состояние → адрес своего экрана; диалог НЕ наследует никогда). **Недостающее решает режим**: interactive называет нужное ОДИН раз (`need` + `ask`, ответ записывает `daiver_track_manifest` — после записи вопроса нет); autonomous — `blocked: no-implementation` (с именем кадра) или `blocked: no-open-recipe` с `supply`/`nextStep`: адрес и клик не выдумываются. Диалог без адреса спрашивает адрес страницы, на которой он открывается, и отдельно рецепт; диалог и состояние без `open` — всегда нужен рецепт (`RECIPE_HOW`: вырабатывается ОДИН раз вместе с человеком по исходникам и картинке).
- **Dev-сервер** (`devserver.start`, его зовёт 7.2): interactive НЕ стартует его никогда (отказ ДО запуска любого процесса); автономный запускает ЗАПИСАННЫЙ `devCommand` оболочкой (`sh -c` — переменные окружения и `&&` работают) в своей группе процессов (`proc.popen_group`), опрашивает адрес (любой HTTP-ответ — сервер жив; прокси не используются; не-ASCII путь кодируется), и гарантированно убирает ВСЮ группу (`proc.kill_group`; повтор — пустая операция; `with` и `stop()`); уже отвечающий адрес — чужой сервер: не стартует второй, не глушится (`owned: false`). Не поднялся за `ready_timeout`, умер раньше (с кодом и хвостом вывода в ответе), команды нет, каталога нет — `DevServerFailed.blocked` = `blocked: implementation-unreachable` с `supply`.
- **Пин захвата** (INV-C23): первая записанная итерация (`state.record`) закрепляет в `verify-state.json` → `capture` рецепт (actions, clipSelector, waitForSelector, waitForGone) и viewport из метаданных снимка; `daiver_screenshot` на цель implementation внутри `verify/` отказывает на любое отличие (сообщение называет, что именно не совпало), `record` предупреждает о просочившемся дрейфе, пин не перезаписывается. Не пинятся: адрес (порт dev-сервера меняется), `waitMs`, цель reference и baseline; до первой записи захват свободен (рецепт вырабатывается). `daiver_verify_state` показывает `pinned` и добавляет это в `nextStep`.
- **Мутационная проверка** (одноразовый скрипт): 23 мутанта (interactive стартует, чужой сервер, HTTP-ошибка, группа, ранняя смерть, таймаут, хвост, лог, схема адреса, оболочка, прокси, режимы, диалог, пин по viewport / рецепту / отсутствию / полноте, перезапись, предупреждение, принудительность) — убиты все, кроме эквивалентного «повтор stop» (идемпотентность держит и сам `kill_group`).

**Не проверено данными.** Настоящий `vite` / `webpack-dev-server` (время старта; сервер, отвечающий раньше готовности сборки, — ответственность `waitMs` захвата), Windows (`cmd /c`, `taskkill /T`), как слабая модель читает `need` / `blocked` и выбирает clip; выработка рецепта с человеком по картинке — бриф, не код (единственное, что форсится кодом: пин после записи).
