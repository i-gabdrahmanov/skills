# 3.1 — build_state: возобновляемая сборка по секциям

**Этап:** 3 · **Зависит от:** 1.8 · **Статус:** done
**Спека:** §13.3–13.4 · **INV:** C10, G1, G2 · **QG:** U13

## Зачем
Прогон, остановленный на секции 3 из 6, продолжается с `next`, а не с нуля; изменилась секция в
макете — пересобирается только она.

## Что сделать
`daiver/build_state.py`; `<frame>/build-state.json` пишет только движок. Инструменты:
- **`daiver_build_state(track, frame?)`** — инициализация из `plan.json.buildOrder` (все pending,
  версия 1) или сверка с ним: хеш секции не изменился — done остаётся; изменился — done → stale;
  новые id — pending; удалённые — выпадают; порядок — по buildOrder; имя может обновиться.
  Возвращает `next` (первая pending/stale) и прогресс.
- **`daiver_build_state_set(track, frame?, sectionId, status, outputs?, hash?)`** — status
  `in_progress` | `done`; на done — `outputs` (пути ОТ КОРНЯ ПРОЕКТА или абсолютные, никогда голые
  имена файлов: код-гейт откроет именно их) и `hash` секции из `daiver_section`. Неизвестный id —
  ошибка; статус вне перечня — отказ схемы; несуществующий output — предупреждение, которое
  разбирается немедленно.
- **Контракт для статуса (1.10):** лестница `daiver_status` читает `build-state.json` → `sections[].status` ∈ pending|in_progress|done|stale (список не пуст, иной файл — «нет» + warning); `building` ⇔ есть секция не `done`, поэтому пометка `stale` возвращает проверенный кадр в сборку — не ломать.

## Готово, когда
- `test_build_state.py`: инициализация; продолжение с `next` после частичной сборки; stale только у
  изменённой секции; новые/удалённые секции; outputs — голое имя файла отклоняется, отсутствующий
  путь даёт предупреждение; неизвестный id — ошибка.

*Заметка (2.6).* Формат `plan.json` (schema 1, пишет только `daiver_plan_write`): `buildOrder: [{id, name, hash}]` — реальные id секций с хешами в порядке сборки
(создатели общих local-компонентов → потребители → остальное; occluded и пролог не входят), `weightBudget` — бюджет, при котором эти id секции (сборка зовёт
`daiver_section(sectionId, weightBudget=plan.weightBudget)`, а не конфиг: он мог измениться), `sections[]` — `{id, name, hash, weight, nodes[]}`, `locals[]` — имена общих
local-компонентов и секция-создатель. Сверка `daiver_build_state` — по `buildOrder[].hash` против нынешнего хеша секции: `plan.json` не перечитывать целиком (только `buildOrder`
и `weightBudget`). Перегенерированный план при смене требования/вердиктов/спек — `stale` у контракта; подпись при этом слетает (план в `sections[].nodes`).

## Результат
Модуль `daiver/build_state.py` (формат, сверка с планом, переходы, читатель для гейта сборки); в `tools.py` — два инструмента **`daiver_build_state(track, frame?)`** и
**`daiver_build_state_set(track, frame?, sectionId, status, outputs?, hash?)`** (оба — в `EXPECTED_TOOLS`); в `status.py` менялись только тексты: ступень `planned` называет
`daiver_build_state`, `building` — «первая секция не done» (разбор `build-state.json` лестницей не тронут, `test_status_ladder.py` зелёный как был). Тесты: `test_build_state.py` (95: инициализация,
возобновление, стухание, новые и удалённые секции, переходы, outputs, повреждённый файл, запись, читатель гейта, «Modal», реестр, гигиена модуля). Мутационно проверено 70 правил (одноразовый
скрипт: копия дерева, правка текста модуля): три выжили с первого прогона (каталог на месте записанного файла не считался отсутствующим; пустой `sectionId` отличался от неизвестного только
словами; предупреждение загрузчика канона не доходило до ответа) и получили тесты; итог 70/70.

- **Данные образца.** «Modal» — ОДНА секция (`2:153702`, «Modal», `hash` `0ccf768ee9d7`, бюджет 24000 — дефолт конфига, он же `weightBudget` плана и состояния). `build-state.json`: 199 Б после первой
  сверки, 286 Б после `done` с двумя outputs; ответ `daiver_build_state` — 14 строк (`indent=1`), `daiver_build_state_set` — 16, от числа секций они не растут (30 секций — те же ~14 строк: `next` и
  прогресс, а не список). `hash` из `daiver_section` равен записанному в состоянии; цикл in_progress → section → done переводит ступень `building` → `built`, `gate_problems` пуст.
- **Формат.** `{schema:1, track, frame, weightBudget, sections:[{id, name, hash, status, outputs?}]}`; «версия state = 1» спеки — это `schema`. Секции в порядке `buildOrder`, ключи отсортированы, времени и
  путей машины нет. Лестница 1.10 читает файл как прежде (ей важны `sections[].status`), остальных полей не видит. `weightBudget` лежит в файле, чтобы ответ `set` называл бюджет для `daiver_section` без
  чтения плана: сборка берёт секции при бюджете плана, а не конфига (id секций зависят от него).
- **Сверка.** Источник секций — `buildOrder` плана (читаются только он и `weightBudget`). Хеш прежний — статус и outputs сохранены; другой — `done` → `stale` (outputs прежней сборки остаются, `next.outputs` называет
  файлы для правки на месте), pending / in_progress / stale статус сохраняют, хеш обновляется; новые id — pending; удалённые выпадают; порядок и имена — по плану. `next` — первая секция не `done`, в том числе
  оставленная `in_progress` (иначе прерванный прогон не вернулся бы к ней никогда). Ничего не изменилось — файл не пишется и замок не берётся (читающий вызов следов не оставляет).
- **План против макета.** Перед сверкой хеши `buildOrder` сличаются с `outline.section_list` нынешнего канона при бюджете плана; расхождение (канон пересобран, секция исчезла) — отказ «план не соответствует
  макету» с лечением (пересобрать план — подпись при этом слетит), состояние не трогается. Это единственное место, где 3.1 читает канон; оно же замыкает путь стухания: макет сменился → план пересобран →
  состояние сверено → стухла только изменённая секция.
- **Переходы (код, не бриф).** `status` — `in_progress` | `done` (`pending` и `stale` выставляет сверка, иначе отказ схемы). `done` только из `in_progress` (повторный `done` обновляет outputs, тот же вызов — без
  изменений); `in_progress` только для `next` (порядок плана: создатель общего local-компонента раньше потребителей, прогон не рестартует с первой секции); `done` не воскресает; `done` без `outputs` и `hash` не
  бывает. `hash` — `section.hash` из `daiver_section`, сверяется с записанным и в отказах НЕ называется (иначе его списали бы из отказа, не вызвав `daiver_section`); неизвестный id — ошибка с перечнем настоящих.
  Нарушения аргументов собираются в одно сообщение, нарушения состояния (перескок, чужой hash) — вторым заходом, тоже все сразу.
- **outputs.** Пути ОТ КОРНЯ ПРОЕКТА; абсолютный внутри репо приводится к такому (путей машины в файле нет), отсортированы, без повторов, ≤ 50 штук и ≤ 300 знаков. Отказ: голое имя файла (и `./X.tsx`), `..`, `~`,
  обратные слэши, управляющие знаки, путь вне репо или по ссылке за его пределы, корень, каталог. Несуществующий путь — НЕ отказ, а `warnings` (так в спеке), и он повторяется в каждом `daiver_build_state`, пока файла
  нет (каталог на месте записанного файла — тоже «нет»).
- **Запись.** Приёмом 2.4/2.6: `plan.write_atomic` (tmp + replace байтами) под замком `ground/build-state.lock` со свежим чтением внутри замка — запись соседа, сделанная между чтением и замком, не теряется (тест
  подменяет замок). Повреждённый файл (не JSON, не та форма, чужой кадр, `done` без outputs…) — отказ с причиной обоим инструментам, молчаливого сброса нет; удаляет файл человек, сборка тогда начнётся с первой секции.
- **Граница.** Не сделано, как и просили: бриф и пролог `ui-build`, `ui_gate.py build` (3.2; для него готов читатель `build_state.gate_problems` — нет состояния / не сверено с планом / секции не done / outputs не на
  диске; в `ui_gate.py` НЕ подключён, гейт по-прежнему exit 3), хук `ui-guard` (3.3), `state-write-guard` и `phase_tools` (3.4), несколько кадров (6.1), регионы и ревизии (6.2/6.3).
- **Решено там, где спека свободна или противоречива.** `stale` вместо «stale→pending» (INV-G2, U13) — по §13.4, статусу лестницы 1.10 и тексту задачи; порядок и «перескок» (спека проверяет только неизвестный id и
  enum); сверка плана с макетом; пределы числа и длины outputs; каталог в outputs — отказ; один замок на репо (`ground/build-state.lock`), а не на кадр.
- **Отклонения** — строки README: сигнатуры (`track` вместо `statePath`, секции читает код), `stale` вместо «stale→pending», проверки переходов сверх спеки, правило pull «файл есть — собран» теперь запирает кадр
  после первой сверки.
- **Не проверено данными.** Боевых экранов и прогонов сборки нет: поведение на большом числе секций (синтетика до 30); секция, чей корень решён `ignore`, ничего не строит, а `outputs` у `done` обязателен — тупик
  (README → «Нужно от пользователя»); пределы `MAX_OUTPUTS` / `MAX_PATH`; как слабая модель читает отказы переходов и `nextStep` (X.4); строгий порядок может мешать, если модель застрянет на секции (выхода
  «пропустить» нет — решает человек); стухание через повторный pull недостижимо до 6.3 (pull запирает кадр, см. отклонения) — достижимо через пересобранный план (канон пересобран движком, смена бюджета).
