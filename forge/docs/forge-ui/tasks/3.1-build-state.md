# 3.1 — build_state: возобновляемая сборка по секциям

**Этап:** 3 · **Зависит от:** 1.8 · **Статус:** todo
**Спека:** §13.3–13.4 · **INV:** C10, G1, G2 · **QG:** U13

## Зачем
Прогон, остановленный на секции 3 из 6, продолжается с `next`, а не с нуля; изменилась секция в
макете — пересобирается только она.

## Что сделать
`daiver/build_state.py`; `<frame>/build-state.json` пишет только движок. Инструменты:
- **`daiver_build_state(track, frame?)`** — инициализация из `plan.json.buildOrder` (все pending,
  версия 1) или сверка с ним: хеш секции не изменился — done остаётся; изменился — done → stale;
  новые id — pending; удалённые — выпадают; порядок — по buildOrder; имя может обновиться.
  Возвращает `next` (первая pending/stale) и прогресс.
- **`daiver_build_state_set(track, frame?, sectionId, status, outputs?, hash?)`** — status
  `in_progress` | `done`; на done — `outputs` (пути ОТ КОРНЯ ПРОЕКТА или абсолютные, никогда голые
  имена файлов: код-гейт откроет именно их) и `hash` секции из `daiver_section`. Неизвестный id —
  ошибка; статус вне перечня — отказ схемы; несуществующий output — предупреждение, которое
  разбирается немедленно.
- **Контракт для статуса (1.10):** лестница `daiver_status` читает `build-state.json` → `sections[].status` ∈ pending|in_progress|done|stale (список не пуст, иной файл — «нет» + warning); `building` ⇔ есть секция не `done`, поэтому пометка `stale` возвращает проверенный кадр в сборку — не ломать.

## Готово, когда
- `test_build_state.py`: инициализация; продолжение с `next` после частичной сборки; stale только у
  изменённой секции; новые/удалённые секции; outputs — голое имя файла отклоняется, отсутствующий
  путь даёт предупреждение; неизвестный id — ошибка.

*Заметка (2.6).* Формат `plan.json` (schema 1, пишет только `daiver_plan_write`): `buildOrder: [{id, name, hash}]` — реальные id секций с хешами в порядке сборки
(создатели общих local-компонентов → потребители → остальное; occluded и пролог не входят), `weightBudget` — бюджет, при котором эти id секции (сборка зовёт
`daiver_section(sectionId, weightBudget=plan.weightBudget)`, а не конфиг: он мог измениться), `sections[]` — `{id, name, hash, weight, nodes[]}`, `locals[]` — имена общих
local-компонентов и секция-создатель. Сверка `daiver_build_state` — по `buildOrder[].hash` против нынешнего хеша секции: `plan.json` не перечитывать целиком (только `buildOrder`
и `weightBudget`). Перегенерированный план при смене требования/вердиктов/спек — `stale` у контракта; подпись при этом слетает (план в `sections[].nodes`).
