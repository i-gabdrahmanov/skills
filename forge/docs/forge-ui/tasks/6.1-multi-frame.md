# 6.1 — Мультикадровый трек

**Этап:** 6 · **Зависит от:** этап 4 · **Статус:** done
**Спека:** §4.2 (переезд в frames/), §13.1, §14.1 · **INV:** C3, C39 · **QG:** P3 (часть)

## Зачем
Фронт-часть стори — часто несколько кадров (экран, модалка, состояние). Кадры одной фичи
равноправны и строятся в ОДИН модуль.

## Что сделать
- Добавление второго кадра (`daiver_pixso_pull(..., frame=<имя>)`) переносит семью main в
  `frames/main/`, переписывает пути в track.yaml, state-файлах и отчётах; ответ сообщает
  «LAYOUT — …»; старый путь продолжает резолвиться по новому месту; обратно ничего не движется.
- Собственные файлы трека не переезжают никогда: `track.yaml`, `run.json`, спеки, `ui-plan.md`,
  `resolution-report.md`, `verify-report.md`, `verify-decisions.json`.
- Резолв, план, сборка — по кадрам в порядке манифеста; место корня не-первичного кадра в модуле —
  решение плана (поле плана), не выбор сборки. Отчёт итерации — один на трек с полосой кадров.
- Предупреждения вслух: `screenRoots > 1` (это N отдельных кадров), два кадра на одном URL — ошибка
  именования.

## Готово, когда
- `test_multi_frame.py`: второй pull переносит main и переписывает пути; старый путь резолвится;
  файлы трека на месте; статус считает ступень по фронтирному кадру; один модуль в плане.

*Заметка (3.2).* `ui_gate.py build` (`daiver/build_gate.py`) требует `build-state` у КАЖДОГО кадра трека, в том числе у кадров-состояний (`stateOf`) — пока их не строит 6.2, трек с ними гейт не пройдёт. Правила «оболочку пишет
последняя секция порядка плана» и «каталог модуля — `<outputDir>/<имя кадра>`» заведены для одного кадра; для трека из нескольких кадров («в ОДИН модуль», INV-C39) решить заново: чьё имя у каталога, где корень не-primary кадра.

## Результат
Новых инструментов нет: второй кадр заводит тот же `daiver_pixso_pull`. Код: `daiver/layout.py` (переезд, переписывание путей, старые пути), `daiver/pixso/pull.py` (второй кадр, URL, откат), `daiver/plan.py` + `plan_digest.py` + `plan_contract.py` (решение о месте корня), `verify/report_html.py` (ссылки полосы кадров), `tools.py` (`LAY.redirect` в `_path_inside`). Тесты: `test_multi_frame.py` (**20**), плюс обновлены `test_pixso_pull.py` (вместо отказа «второй кадр — задача 6.1» — отказ «тот же URL») и `test_plan_contract.py` (форма входа плана).

- **Переезд** (`layout.migrate`): когда в треке один кадр с `dir: "."` и тянут второй, семья первого уходит в `frames/<имя>/` переименованиями (байты те же). Семья названа ИМЕНАМИ (`FAMILY`: требование, сырой экспорт, растр, канон, арты, план, резолвы, build-state, verify-state, `verify/`, `versions/`, `baseline/`, имена из манифеста, `goal.*`), а не «всё остальное»: собственные файлы трека (`track.yaml`, `run.json`, `ui-plan.md`, `plan.lock.json`, `resolution-report.md`, `verify-report.md`, `verify-decisions.json`, телеметрия, спеки) и чужие файлы пользователя остаются на месте байт в байт. Порядок: пишется файл нового кадра → переезд → запись манифеста; сбой переезда или записи манифеста откатывает перенесённое и убирает файлы нового кадра (манифест не теряет первый); цель занята — отказ ДО любой записи. Третий кадр и повторный pull переезда не делают («обратно ничего не движется» и «второй раз не переезжает»). Ответ: `layout {message: «LAYOUT — …», movedFrame, moved[], rewritten[]}` и та же строка в `notes`.
- **Пути**: после переезда `.daiver/tracks/<T>/<имя семьи>…` переписывается внутри JSON и Markdown переехавших записей (`verify-state.json`: `history[].dir`; артефакты итераций), `verify-report.md` пересобирается из состояния. НЕ переписываются `plan.json`, `plan.md`, `resolutions.json` и `resolution-report.md`: их хеши связаны с подписью человека (`plan.lock.json`, `--bind-file`) — переезд кадра подпись не отзывает (тест: хеши и байты плана те же, `daiver_plan_write` повторно — `written: false`). Чужой трек и уже новый путь не трогаются.
- **Старый путь резолвится**: `layout.redirect` — если по `.daiver/tracks/<T>/<имя семьи>/…` ничего нет, а в `frames/<первичный>/…` есть, инструменты (через `_path_inside`: `iterationDir` и др.) берут новое место. Собственные имена трека не переадресуются (файл решений КАДРА не подменяет файл решений трека); есть что-то по старому пути — оно и берётся.
- **Предупреждения вслух**: `screenRoots > 1` (уже было в slim) ретранслируется в `warnings` ответа pull; два кадра ОДНОГО трека на одном `frameUrl` — отказ (ошибка именования), до любых изменений на диске; тот же URL в другом треке — предупреждение (как раньше).
- **Один модуль в плане** (решение, а не выбор сборки): у не-первичного кадра без `stateOf` в `plan.json` есть `module: {name: <первичный кадр>, root: {mode: own-file | inside-primary, component, host?, reason?}}`. Модель задаёт `plan.placement` в `daiver_plan_write`; по умолчанию own-file с компонентом по имени кадра (`Dialog`); `inside-primary` требует `host` — id узла из канона первичного кадра (проверяется кодом). У первичного кадра и кадра-состояния поле не принимается (состояние строится ВНУТРИ экрана — 6.2), и их план не меняется ни байтом (поэтому подпись плана не слетает от появления второго кадра). Правка `module` руками — план `stale`. Видно человеку: раздел «Модуль» в `plan.md` кадра, в `ui-plan.md` (только при наличии не-первичных кадров — дайджест прежних треков не изменился) и строка «Один модуль трека…» в вопросе подписи. Каталог модуля — `<outputDir>/<имя ПЕРВИЧНОГО кадра>` один на трек (брифы `ui-design` / `ui-build` обновлены).
- **Статус**: ступень трека считает по первому нечистому кадру в порядке манифеста (так было с этапа 1; тест закрепляет и остальные кадры в «Далее по треку»).
- **Отчёт**: `verify-report.md` один на трек (с 4.8); у `report.html` чип другого кадра — относительная ссылка на ПОСЛЕДНИЙ отчёт того кадра (страница самодостаточна: ссылки только на соседние файлы), текущий кадр и кадры без отчёта — не ссылки.
- **Мутационная проверка** (одноразовый скрипт, байткод — во временный каталог): 25 мутантов (семья, подпись, чужой трек, откат, предпроверка, пересборка отчёта, redirect, URL, хвост нового кадра, решение о модуле, host, нормализация основания, повторная проверка, режим по умолчанию, дайджест, строка вопроса подписи, ссылки отчёта, tools). Убиты все, кроме пары «предпроверка цели» / «проверка цели в `migrate`»: каждая по отдельности избыточна (вторая — страховка от гонки), снятые обе вместе тест ловит (отказ без записи файлов нового кадра). Выжившие при первом прогоне — имена вне семьи в `redirect` (дописан тест: файл решений кадра) и строка вопроса подписи (дописан тест `test_plan_contract`).

**Заметка о мутационных прогонах.** `/usr/bin/python3` (Xcode, macOS) пишет байткод НЕ в `__pycache__`, а в `~/Library/Caches/com.apple.python/<путь>`: мутант и восстановленный исходник одного размера, записанные в одну секунду, получали чужой байткод. Прогоны 5.4–6.1 перезапущены с `PYTHONPYCACHEPREFIX` во временный каталог на каждый мутант — результаты ниже в этом файле и в задачах 5.4 / 5.5 перепроверены.

**Не проверено данными.** Переезд на Windows (файл, открытый другой программой, не переименуется — сбой с откатом, не полупереезд), очень большие `verify/`, треки, переведённые вручную в `frames/` без переезда; боевой план из нескольких кадров (как модель выбирает own-file / inside-primary и называет `host`), как слабая модель разводит «первичный кадр» и «остальные» при сборке в один каталог; ссылки между отчётами при открытии `report.html` с другого диска (относительные пути).
