# 6.4 — Правка существующей страницы (page baseline)

**Этап:** 6 · **Зависит от:** 6.3 · **Статус:** todo
**Спека:** §12.2, §13.7 (page), §14.4.6 (baseline.standing), §20.4 (proposeSources: MIN_TEXT_LENGTH 3,
limit 8, maxFiles 3000) · **INV:** C18, C19, F18 · **QG:** U22, P4

## Зачем
Страница написана людьми, не forge-ui. Изменение по макету правит её точечно и отличает свои
регрессии от старых расхождений.

## Что сделать
- На ui-design: «страница уже есть?» → `sources` — находятся по конвенциям проекта → роутеру →
  текстам страницы (инструмент **`daiver_propose_sources(track, frame)`**: тексты канона ≥ 3
  символов, до 8 кандидатов, обход до 3000 файлов), подтверждаются ЧТЕНИЕМ, не угадываются;
  `scope` change | page. Без sources — `blocked: no-sources`.
- Захват базы ДО правок кода: `daiver_screenshot` → `daiver_verify_compare(iterationDir=<frame>/baseline)`
  → `daiver_code_compare(iterationDir=baseline)` → `baseline:{kind:"page"}`. Пропуск — только если
  работающей страницы нет вовсе, и это говорится открыто.
- Сборка в файлы `sources`: место каждого региона `location` own/inside/ancestor (file:line из
  код-гейта); файл читается до правки (чужой код — домашний стиль); вне регионов ничего не
  реформатится, не переименовывается. `ui-guard` для scope page разрешает запись в sources, а не в
  outputDir.
- Verify: `baseline.standing` — каждый дефект классифицируется change / pre-existing / regression по
  ключу (code, designId, свойства rows) / (code, element), никогда по id дефекта; scope change —
  pre-existing не блокирует; scope page — считается всё; три числа словами в nextStep.

## Готово, когда
- `test_page_baseline.py`: синтетическая «ручная» страница + база → классификация standing при
  scope change и page; propose_sources находит файл по текстам; проверка «вне регионов дифф нулевой».

*Заметка (2.6).* Поля кадра `sources` (список файлов страницы от корня репо) и `scope` (change | page, только вместе с `sources`) уже в `track.yaml` и задаются
`daiver_track_manifest` (`track.py`, 2.6): контракт плана проверяет их пунктами `sources` (файлы на диске, scope задан; блокирует) и `baseline` (папка `<кадр>/baseline` не пуста; блокирует) для
кадра с непустыми `sources`; кадр без `sources` строится с нуля, эти пункты «н/п». Здесь остаются поиск файлов (`daiver_propose_sources`), захват базы, запись `baseline: {kind}` и поток правки.
Записи об «открытом пропуске базы» формата нет — если он нужен, завести его здесь и дать контракту прочитать.

*Заметка (3.2).* Бриф `ui-build` исходит из нового модуля: пролог (конвенции, `plan.md`, карта цветов, пустой `mocks.ts`) идёт в каждом запуске, каталог — `<outputDir>/<имя кадра>`. Для кадра с `sources` (правка существующей
страницы) пролога нет — scaffold существует, `mocks.ts` редактируется, строится в файлы `sources`; эту ветку брифа и гейта добавляет 6.4 (сейчас бриф кадр с `sources` не отличает).

*Заметка (3.3).* `ui-guard` охраняет только `project.outputDir` (запись вне `ui-build`, подпись плана, инлайн-svg). Файлы `sources` кадра с правкой существующей страницы лежат вне outputDir и хуком НЕ охраняются:
чтобы «`ui-guard` для scope page разрешает запись в sources, а не в outputDir» стало правдой, расширить `_judge_write` в `hooks/ui-guard.py` — цели записи там сверяются с `outputDir` функцией `_in_output`; добавить
пути `sources` активного трека (список уже собирает `_extras` для ключа кеша подписи) и применять к ним те же три правила (шаг `ui-build`, подпись, инлайн-svg). Что делать с записью в outputDir при scope page — решить здесь.

*Заметка (3.4).* `baseline/**` и `versions/**` под `.daiver/tracks/<KEY>/…` охраняет `state-write-guard` — снимок базы страницы и ревизии пишет только движок. `daiver_propose_sources` решает по тому же правилу, что и остальные инструменты: чей он — `phase_tools`
шага `ui-design` или список свободных (`test_every_engine_tool_has_an_owner` не даст добавить его молча). Файлы страницы (`sources`) вне `.daiver/` — обычный прод-код фронта: `.tsx/.jsx/.vue/.svelte` классифицируются R2 (не тест), запись в них идёт по правилам `ui-guard` (см. заметку 3.3).
