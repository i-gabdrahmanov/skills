# 2.3 — ds_inventory / ds_lookup / ds_details

**Этап:** 2 · **Зависит от:** 2.2 · **Статус:** done
**Спека:** §10.3, §11.1 п.1, §20.4 (lookup limit 5, схема 1..20; details ≤ 10 за вызов) ·
**INV:** A2, A4, A5 · **QG:** U9

## Зачем
Детерминированный шортлист кандидатов вместо «модель читает библиотеку и выбирает на глаз».

## Что сделать
`daiver/ds_lookup.py`; инструменты:
- **`daiver_ds_inventory()`** — список компонентов из КОММИТНУТОГО контракта (никогда не
  пересканирует); вызывается ОДИН раз на трек до резолва; источник не отвечает →
  `blocked: library-source-unreachable` до старта резолва.
- **`daiver_ds_lookup(figmaName, variants?, textSlotKeys?, limit?)`** — нормализация имён (camelCase
  и разделители рушатся одинаково); ранжирование — код: точное имя — максимум; близкое имя
  (вхождение, общие части) — с кредитом объявленных вариантов; значение варианта, которое компонент
  принимает, — баллы; наличие текстовых слотов — баллы; малый бонус за документированность
  сторями; равные баллы — по имени (никогда по порядку вставки); limit 5 (1..20). Пустой список —
  настоящий ответ («в библиотеке нет» → local).
- **`daiver_ds_details(components[≤10])`** — описание, дефолты, deprecations, примеры сторей (JSX)
  для 1–2 финалистов.

## Готово, когда
- `test_ds_lookup.py`: перемешанный вход → тот же порядок; точное имя побеждает; пустой список —
  `[]` без ошибки; details > 10 — отказ; inventory читает файл, а не сканирует.

## Результат
Инструменты **`daiver_ds_inventory()`**, **`daiver_ds_lookup(figmaName, variants?, textSlotKeys?, limit?)`**, **`daiver_ds_details(components)`** (`tools.py`,
три строки в `EXPECTED_TOOLS`), движок `daiver/ds_lookup.py` (`load`, `inventory`, `lookup`, `details`, `rank`, `credit`, `import_statement`), абзац в брифе
`SKILL.md`, `test_ds_lookup.py` (119 тестов, QG U9). Мутационно проверено 34 правила (одноразовый скрипт, подмена в памяти) — все пойманы (мутант «storybook-mcp не
отказывает» в первой версии скрипта был холостым — переписан и пойман).

- **Чтение — только документ.** Пару читает `ds_requirements.load_pair(root)` (схема, смысл, один хеш источников); библиотеку инструменты не открывают и не
  сканируют: в тесте `build/discover/read_entries/scan_py/check/sources_hash` подменены исключением, а три инструмента отвечают. Пары нет / она битая / документы не
  согласованы / построены для другого `library.source` или `scanPaths` → `LibraryUnreachable` (у всех трёх одинаково): сообщение начинается
  `blocked: library-source-unreachable — <причина>` и называет `daiver_ds_requirements` (исключение несёт `reason` — для 7.1). **Хеш-устаревание** (файлы библиотеки
  менялись после сборки) инструменты НЕ проверяют — это чтение библиотеки на каждый вызов; его говорит `daiver_ds_requirements(check:true)` (тест закрепляет это разделение).
  `library.source = storybook-mcp` — отдельный отказ с названным сервером (документов там нет по построению), «проект не инициализирован» — тоже отдельный. `load_pair` на
  каждый вызов без кэша: 11 мс на 100 компонентов, 70 мс на 500×20 пропов (замер на синтетике); правка документа видна сразу.
- **Ключ имени — карта (2.1).** Равенство и вхождение — по `component_map.name_key` (второго ключа нет); слова для «целого слова» и «общих слов» — деление по разделителям,
  camelCase (`aB`, `ABc`) и границе буква/цифра, каждое слово — тот же `name_key` (тест: слова склеиваются в ключ карты).
- **Ранжирование** (формулы — в докстринге модуля; ВСЁ из текста спеки §10.3, не из данных): кандидат — только компонент со связью по имени. Уровни: `exact` 1000 (ключи равны; 900, если равно только имя из `title` — имя в коде главнее) >
  `word` 600 (одно имя целым словом внутри другого: Button в PrimaryButton) > `part` 300 (внутри слова: Tab в Tabs) > `shared` 100 (только общие слова ≥ 3 знаков), плюс доля длины
  (0..99; у `shared` — доля общих слов 0..100). Кредиты — только внутри уровня: +10 объявленный вариант (проп с тем же ключом), +15 принятое значение (enum — среди `options`; boolean —
  `true`/`false`; иначе — среди `usedValues`; без «Large → lg», без «ON → true»), +10 текстовый слот (проп вида string | node), +1…5 истории; сумма ≤ 99 — разрыв между уровнями больше,
  поэтому точное имя всегда максимум (тест на свойство + мутанты). Равные баллы — по ключу имени, затем по имени: перемешанный документ даёт тот же ответ побайтно, порядок
  ключей `variants`/слотов на входе — тоже. Синонимов, опечаток и расстояния Левенштейна нет намеренно («Notification» не найдёт «Alert» — решение модели по inventory).
- **Ответы** (`indent=1` в MCP — поэтому плоские объекты и строки). lookup: `{limit, total, candidates:[{name, score, match, why, import, hasDetails, deprecated?}], note?, limitNote?}`;
  `why` — одна строка («имя совпало · варианты: принимает size=lg; не принимает variant=Default; нет пропа Foo · слоты: label; нет пропа Title · истории: 4»), значения — в написании ДС;
  `import` — готовый statement в том же виде, что у карты (`import { X } from "…";`, default, `{ Y as X }`, составной `Form.Item` → корень `Form`; не складывается в код — `null`).
  Пустой список — `candidates: []` + `note` (→ local), не ошибка. `limit` 5 по умолчанию, вне 1..20 приводится к границе (`limitNote`; спека: «схема клампит»), не целое — отказ.
  details: компоненты в порядке запроса, имя без учёта регистра/разделителей (точное имя сильнее ключа; два компонента с одним ключом — отказ), неизвестное — отказ с «похожими по
  имени» (тот же ранжировщик) и подсказкой; > 10 — отказ; пропы строкой «`enum: "sm" | "lg"; required; default "md"; used …; DEPRECATED → X — описание`» (required первыми),
  примеры — `{имя истории: JSX}`, deprecations — списком (в т. ч. deprecated-пропы помечены и в строке пропа). inventory: `Имя [DEPRECATED → замена] (группа) — описание (≤ 64)` по ключу имени
  + счётчики шапки (`count`, `stories`, `withDetails`, `withoutImport`, `deprecated`).
- **Потолки размера — код, не надежда.** lookup: ≤ 20 кандидатов, `why` ≤ 220, `deprecated` ≤ 140 (худший случай — 20 кандидатов, длинные пути, 30 вариантов и 30 слотов на входе, ≈ 12 КБ; по умолчанию ≈ 3 КБ).
  details: цель 26000 знаков на вызов делится на число компонентов, но не больше 6000 на один; пять ступеней (`LEVELS`): сначала проза `docs`, затем примеры, описания пропов, хвост пропов (имена
  остаются в `moreProps`); `cut` называет убранное; deprecations ступенями не режутся (≤ 12 записей). inventory: потолок 32000 — сначала отбрасываются описания, затем остаются одни
  имена; список имён не режется никогда. Всё это — на синтетике с огромными документами (десять компонентов с десятками КБ прозы и 60 пропами по 40 значений укладываются в цель).
- **Решено там, где спека свободна** (строки — в README плана): `title` (последний сегмент) — второе имя компонента для связи по имени; в кандидате `deprecated` (компонент помечен, не прячется и не штрафуется);
  отказ на устаревание по `library.source`/`scanPaths`; `details` принимает список (спека §10.3 — `component`, §20.4 — «≤ 10 за вызов»).

**Для 2.5 и 4.5.** Резолв зовёт `daiver_ds_inventory` один раз на трек и обязан остановиться на `blocked: library-source-unreachable` (INV-A4); на кандидата — lookup и details 1–2 финалистов. Код, которому
нужен контракт (DS-гейт 4.5), читает его теми же `ds_lookup.load(root)` / `ds_requirements.load_pair` — отказы одинаковые. Инвентарь субагентам передаёт оркестратор (в описании инструмента это сказано, но
запретить повторный вызов изнутри инструмента нельзя — у него нет аргумента трека; если боевой прогон покажет повторные вызовы, это правило `ui-guard` (3.3), а не движка).

**Не проверено данными.** Боевой ДС нет: веса, пороги (`MIN_PART` 3, кредиты 10/15/10/5, разрывы уровней), бюджеты ответов и сама идея «`part` — вхождение внутри слова» выведены из текста спеки и проверены на синтетической
`fake-ds` (10 компонентов) и построителях в тесте; как расходятся имена макета и кода в настоящей библиотеке (префиксы вроде `Ui`, множественное число, синонимы) — неизвестно, ложные `part`-совпадения («Tab» ⊂ «Table»)
возможны и честно помечены уровнем. «Принимает значение» для `kind: string/number` опирается на `usedValues` как словарь — смысл на реальных сторях не проверен. Как слабая модель читает `why`/`match` и формулировки
отказов — проба боевого прогона (X.4); реальный MCP-клиент (GigaCode) не гонялся — JSON-RPC-сессия в тесте.
