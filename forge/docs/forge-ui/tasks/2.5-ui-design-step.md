# 2.5 — Шаг ui-design: бриф, отчёт резолва, подтверждения, layoutHints

**Этап:** 2 · **Зависит от:** 2.3, 2.4 (и весь этап 1) · **Статус:** done
**Спека:** §11.1, §10.4–10.5, §11.4, §16, §3.3 (кто зовёт Pixso) · **INV:** A3, A4, C5, C6, C7, F7, B8,
F4 · **QG:** N5, R2/R4 (в боевом прогоне)

## Зачем
Собрать в один шаг forge всё, что daiver делает между утверждённой спекой и планом: макет → канон →
компоненты → решения по раскладке — с вопросами человеку, пока он рядом.

## Что сделать
- Бриф `ui-design` в `skills/forgeui/SKILL.md` (субагент; вопросы — `pending_questions`):
  1. `daiver_status`; кадры — ТОЛЬКО из таблицы «Кадры» `ui-spec.md`.
  2. Pixso: агент просит Pixso MCP пользователя сохранить DSL кадра В ФАЙЛ (или пользователь
     экспортирует сам) → `daiver_pixso_pull(dslPath)`; DSL в контекст не вставлять; растр →
     `daiver_track_manifest`/goal image; SVG иллюстраций → `daiver_svg_assets`.
  3. `daiver_normalize` → `daiver_outline`.
  4. Список библиотеки ОДИН раз: storybook-mcp — имена у его MCP; stories/sources —
     `daiver_ds_inventory`. Не отвечает — СТОП `blocked: library-source-unreachable`.
     *Контракт 2.3:* инструмент отказывает сообщением, начинающимся `blocked: library-source-unreachable — <причина>` (пары нет / битая / устарела по
     `library.source`/`scanPaths`) — это и есть останов фазы; при `storybook-mcp` он отказывает иначе (спрашивать MCP-сервер). Список субагентам передаёт
     оркестратор: запретить повторный вызов изнутри инструмента нельзя (у него нет трека) — при необходимости это правило `ui-guard` (3.3).
  5. По каждому кандидату: `resolve_query` → правило карты (high) | fuzzy (storybook MCP либо
     `ds_lookup` + `ds_details` финалистов) → `resolve_finalize`.
     *Контракт 2.3:* `daiver_ds_lookup` → `candidates:[{name, score, match, why, import, hasDetails, deprecated?}]`, `total`; `candidates: []` — настоящий ответ
     «такого нет» → `local`; `match` exact/word надёжны, part/shared — подсказка (смысл — за резолвером, уверенность и rationale — его); `import` — готовый
     statement дословно (`null` — спросить). Финалисты — `daiver_ds_details(components[1..10])`: пропы строками, `propsClosed`, дефолты (не передавать повторно),
     deprecations; `cut` — что код убрал из ответа.
  6. Подтверждения: вердикты на пороге `confirmResolutions` и ниже — вопрос с rationale и ссылкой
     `[id](nodeUrl)`; low — спрашивается ВСЕГДА. Предложение правила карты — вопрос → согласие
     `ui-map-<KEY>` → `daiver_map_append`.
     *Контракт карты (2.1):* сначала `daiver_map_append(dryRun:true)` — проверка и YAML без согласия; показать пользователю; после «да» —
     `record_approval --key ui-map-<KEY> --evidence "<ответ>"`; затем вызов без `dryRun`. Согласие одноразовое — на каждое правило своё «да».
     `icons.fallback` (ask | placeholder) — `component_map.load(root).parsed.icons_fallback`; применяет его резолв.
  7. layoutHints — лестница: декларации `daiver_source_nodes` → картинка (только группировка, при
     `vision: on`) → вопрос. px → flex — только через план.
- Движок: генератор `resolution-report.md` — один файл на трек, `## frame: <name>`, таблица
  эвристических вердиктов (не попаданий в карту) со ссылками на узлы.
- Если инструмента-субагента `resolver` нет — процедура идёт внутри субагента `ui-design` (он и
  есть изоляция контекста) с объявлением одной строкой.

## Результат
Бриф шага — `skills/forgeui/SKILL.md` §3 (восемь пунктов в промпте субагента + §3.1 для оркестратора; прежние абзацы про карту, ДС, библиотеку и
резолв влиты в процедуру, дублей нет). В движке: `daiver/resolution_report.py` (отчёт, политика подтверждений, проверка резолва), инструмент
**`daiver_resolve_report(track)`** (строка в `EXPECTED_TOOLS`; новый инструмент сверх списка спеки — строка README), класс согласий **`ui-resolve`** в
`forge_events.CONSENT_PREFIXES` (+ список в `docs/approval-markers.md`), `ui_gate.py design` по-настоящему проверяет резолв, правки `resolve.py`
(`iconFallback` и `next` → `daiver_resolve_report`) и комментарий порога в шаблоне конфига. Тесты: `test_resolution_report.py` (66: формат, ссылки,
детерминизм, политика, согласие настоящим `record_approval.py`, инструмент, гейт, иконки, золотой отчёт на «Modal»), `test_ui_design_brief.py` (15: doc-lint
брифа), правка `test_daiver_mcp.py`. Мутационно проверено 39 правил (одноразовый скрипт: копия дерева, правка текста модуля и брифа) — 39/39 пойманы с первого
прогона тестов.

- **Данные образца.** «Modal» после резолва: 4 кандидата → 3 строки таблицы (шапка ×2 схлопнута, ссылки на `2:153703` и `22:63141`); ссылки — подстановка
  в шаблон `outline` (`item-id={id}`), тест сверяет каждую с `outline.node_url`; золотой текст отчёта (`GOLDEN_MODAL`) — единственное место, где формат
  зафиксирован целиком. Адрес кадра в образце обезличен, поэтому ссылки ведут на `pixso.example`.
- **Отчёт.** `.daiver/tracks/<KEY>/resolution-report.md`, один на трек; секция `## frame: <имя>` в порядке манифеста; в таблице только эвристические
  вердикты (запись `resolver` и копии INV-B23), попадания в карту посчитаны, но не перечислены; строка — на группу узлов с одним вердиктом (отклонение,
  README); нерешённое названо; предложенные правила карты — блок YAML «как ляжет в файл» (тот же `dryRun`, что у `daiver_map_append`). Чистая функция
  хранилищ + конфига + манифеста: ни времени, ни случайности (тест: порядок ключей хранилища и повторный вызов не меняют байты; в модуле нет `time`/
  `datetime`/`random`). Нет шаблона ссылок (dom/code, нет URL) — голые id и ни одного `](url)`; `inferred:` — голый id; скобки в адресе кодируются.
- **Политика подтверждений — что делает код, а что осталось.** Уже форсил `resolve_finalize` (2.4), здесь не дублируется: форма вердикта, узел — кандидат
  кадра, hit в карте диктует вердикт high, один вердикт на figmaName+variants, компонент обязан быть в библиотеке, `mapRuleProposal` проходит
  `daiver_map_append(dryRun)`. Добавлено в 2.5: (1) `confirm_reason` — чистая функция «спрашивать или нет»: `confirmResolutions` «на пороге и ниже»
  (high — всё, medium — medium и low, low — только low), low — при любом пороге, иконка-плейсхолдер при `icons.fallback: ask`; правило карты и копия
  чужого кадра не спрашиваются (копию спрашивают у эталона); (2) `toConfirm` — готовые строки вопроса (low первыми, кап 20, остальное в файле,
  `toConfirmMore`); (3) подтверждение — согласие `ui-resolve-<KEY>` на sha256 отчёта: без него `confirmed:false`, `ui_gate.py design` — exit 1;
  (4) отчёт устарел или правлен руками — exit 1 (гейт пересобирает текст и сравнивает); (5) устаревшее согласие движок снимает при перегенерации
  (`record_approval` не пишет второе согласие по активному ключу — без этого переподтвердить было бы нельзя); (6) гейт только читает (тест: дерево до и
  после побайтно равно), раздачу эталонов между кадрами делает писатель — `daiver_resolve_report`. **Остаток (не форсится кодом):** `confidence` —
  самооценка слабой модели: «high на всё» обходит вопрос на пороге medium, а вопрос про low задаётся, только если модель записала low честно
  (калибровать уверенность по `match` из `ds_lookup` — догадка без боевых данных, не сделано); то, что человек действительно прочёл список, а не
  ответил «да» на что-то другое, цитата не доказывает (так со всеми согласиями forge); автономия (7.1/7.2: medium → `unconfirmed`, low → `local` без вопроса) — режим прогона здесь не
  читается, подтверждение требуется всегда; полнота кадров относительно таблицы «Кадры» `ui-spec.md` — контракт 2.6 (гейт проверяет кадры, которые есть
  в треке).
- **Решено там, где спека свободна.** Подтверждение — согласие на текст отчёта, а не поле в вердикте (INV-A7 фиксирует форму вердикта); порядок вопросов:
  сначала предложенные правила карты (они меняют вердикты и отчёт), потом один вопрос про вердикты; перед согласием на правило — `dryRun`-YAML из ответа
  инструмента; согласия записывает оркестратор сразу после ответа (цитата сверяется с последней репликой пользователя в основной сессии), субагент их не
  пишет; ответы на вопросы возвращаются субагенту как `<id>: <ответ>`; новые статусы JSON субагента — `blocked` (с причиной) и `stopped` (резолв
  закончен, плана нет); гейт ui-design запускается напрямую, не через `record_gate` (раннер причин не печатает, а закрыть шаг до 2.6 нельзя); путь для
  выгрузки DSL `.daiver/inbox/<кадр>.dsl.json` — подсказка (тест: `daiver_pixso_pull` его принимает). Иконка без правила карты и `nameMap` —
  `local` (плейсхолдер), компонент иконки из набора называет только пользователь и это правило карты (`map-rule`), а не вердикт: `finalize`
  не принял бы ни `component` (иконки нет в основной библиотеке), ни `local` с предложением outcome icon. `layoutHints`: лестница в брифе (декларации
  `daiver_source_nodes` → картинка только для группировки, `goalImageNext` решает движок → вопрос); решения нигде не сохраняются — их место в плане (2.6).
- **Отклонения** — пять строк README (подтверждения, иконки, строка отчёта на группу, resolver внутри `ui-design`, гейт design) и новый инструмент.
- **Не проверено данными.** Боевой прогон (X.4): как GLM читает §3, `toConfirm` и отказы; сколько вопросов выпадает на реальном экране при пороге medium и
  не слишком ли длинна таблица; что умеет Pixso MCP пользователя (строка «Нужно от пользователя»); вложенность субагентов и релей `pending_questions`
  в GigaCode; нагрузка на контекст ОДНОГО субагента при резолве большого экрана (`daiver_ds_details` — до 26 КБ на вызов, кандидатов десятки; отдельного `resolver` на кандидата нет) — если переполнится, субагент отдаёт управление порциями и оркестратор перезапускает его (всё лежит на диске); цепочка «ответ ask_user_question → `record_approval` → gate-guard» для класса `ui-resolve` проверена скриптом (`record_approval.py` с
  цитатой и без), но не хуком на живой сессии; формат ссылки Pixso `item-id` — по спеке (адрес образца обезличен).
