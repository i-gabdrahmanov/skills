# 5.4 — Разметка в отчёте и файл решений verify-decisions.json

**Этап:** 5 · **Зависит от:** 5.3 · **Статус:** done
**Спека:** §14.10 (режим «Пометить проблему»), §14.11 · **INV:** C34, D9 · **QG:** P6

## Зачем
Второй способ ответить на итерацию — богаче чата: решение и заметка на каждый дефект, ручные метки
того, что гейты не увидели, ответ сразу всем кадрам трека.

## Что сделать
- В `report.html`: на каждый дефект — fix (с заметкой) / skip / false_positive; режим «Пометить
  проблему» — hit-test по захвату DOM итерации от меньшего к большему, шаг наружу, прямоугольник
  мышью, подавление нативного drag картинки; id меток `user-<iteration>-<n>`, перенесённые метки
  сохраняют старые id; экспорт решений всего трека — скачивание `verify-decisions.json`, пользователь
  кладёт его в папку трека.
- Повторный `daiver_verify_report` читает файл: answered (fix — заметка ДОСЛОВНО; skip → declined;
  false_positive → `noise:true` с именем решившего), reported (ручные метки: note = вся постановка;
  записываются `source:"review"`, `zone:"vision"`, `severity:"major"`, `problem` = note, pin = box
  при `side:"impl"`), answeredElsewhere (чинится в этом проходе, записывается следующей итерацией
  своего кадра). Инварианты файла — из 4.8.

## Готово, когда
- `test_decisions_ingest.py`: отображение ответов в записи итерации по всем четырём видам;
  `test_report_annotate.py` — headless Chrome через CDP 4.1 кликает по отчёту и экспортирует файл
  (skip без Chrome).

## Результат
Новых инструментов нет: интерактив живёт в `report.html` (`daiver_verify_report`), приём файла — в `daiver_verify_report` и `daiver_verify_state_record` одним кодом (`verify/decisions.py` + `state.reported_marks`). Код: `assets/report-annotate.js` (скрипт страницы, вшивается в отчёт), `verify/report_html.py` (данные для скрипта, сводка приёма), `verify/decisions.py` (метки, `foreign`, `reported`), `verify/state.py`. Тесты: `test_decisions_ingest.py` (**13**, без браузера) и `test_report_annotate.py` (**17**: 16 в настоящем Chrome через CDP 4.1, skip без него, и один статический).

- **Решения на карточках**: у каждого дефекта кнопки «чинить / пропустить / ложное срабатывание», поле заметки, «снять». Ответ уходит в экспорт записью `{id, verdict, note?, reviewer?, decidedAt, frame, snapshot.rows}`: снимок значений нужен, чтобы уехавшие значения переоткрыли решение (4.8). Второй ответ заменяет первый; правка заметки меняет уже данный ответ; пустая заметка не пишется. Имя решившего — поле «Кто решает» над картинками.
- **Пометить проблему**: режим включается кнопкой, без него клики ничего не делают. Клик по реализации — наименьший вшитый бокс снимка под курсором (боксы страницы лежат в `report-data`, обход в ширину, не больше 4000), повторный клик в том же месте — шаг наружу и по кругу; прямоугольник мышью — на любой картинке (рамка зажата в границы картинки, любое направление). Реализация: координаты страницы = пиксели картинки + `clip` захвата; макет: координаты корня кадра (нет числового размера корня — метку на макете отчёт не принимает и говорит почему; отрицательные координаты макета — тоже отказ, файл их не примет). Нативный drag картинки отменён (`dragstart`), выделение отключено. Метка без заметки не добавляется. id метки — `user-<N итерации>-<n>`, следующий `n` берётся после занятых этой итерации и после id дефектов; старые метки сохраняют свои id и едут в экспорт нетронутыми (с `reviewer`/`decidedAt`/любыми полями). Удаление метки убирает её из экспорта и скрывает пин.
- **Экспорт**: кнопка «Скачать verify-decisions.json», то же содержимое — в текстовом поле ниже (копировать руками) и в `window.__daiverExport()`. Файл ВЕСЬ — а не только новое: ранее принятые решения и метки едут как были, записи ДРУГИХ кадров трека (`foreign`) — тоже, иначе скачанный файл стёр бы чужие ответы. Страница называет два места, куда его класть (папка трека — на все кадры; папка кадра — только на этот). Дату решения ставит браузер при ответе; сам отчёт по-прежнему детерминирован (дата — вход).
- **Приём** (`daiver_verify_report` и `daiver_verify_state_record` — один и тот же код): `decisions: {answered: {fix, skip, false_positive, reopened}, reported: [id], answeredElsewhere: [id], unknown: [id]}`; в отчёте ещё `rejectedMarks` (поимённые отказы), в записи итерации отказы идут в `warnings`. fix — заметка дословно, skip → `declined`, false_positive → `noise` с именем решившего. Метка → пункт `source: review`, `zone: vision`, `severity: major`, `problem` и `message` = заметка ДОСЛОВНО (переводы строк и кавычки доезжают), `pin` = рамка при `side: impl` (`designPin` на макете), `nodeId` → `impl`; в историю итерации метка несёт `reported`, `problem`, `pin`/`designPin`, `side`, `impl` (`MARK_KEEP`; у обычных дефектов список прежний). Метка на картинку, которой нет (`iter-N/actual.png`, картинка макета), и метка поверх чужого id отклоняются поимённо; негодная запись файла (пустая заметка, чужая сторона, нечисловая рамка, чужой id) — в `problems`, остальные принимаются. Метка другого кадра не применяется, отдаётся как `foreign`.
- **Мутационная проверка** (одноразовый скрипт): 31 мутант (порядок hit-test, шаг наружу и «по кругу», нативный drag, сдвиг clip, защита режима, обязательная заметка, снимок, перенос чужих кадров, столкновение id, удаление метки, начало координат макета, зажим рамки, кадр решения, пустая заметка, имя решившего, отказ клика на макете, отрицательный бокс макета, порядок боксов, номер следующей метки, метки в отчёте, сводка, вшитые чужие записи, история меток, дословность постановки, пин, применение чужой метки, проверка рамки) — выжили пять (столкновение id с дефектом, начало координат макета, стёртая заметка, отрицательный бокс макета, нулевые боксы в hit-test): дописаны тесты (метка поверх id дефекта, корень кадра не в нуле и в минусе, стёртая заметка у данного ответа, нулевые/нечисловые/безымянные боксы и предел 4000), повторный прогон — убиты все.

**Метки не блокируют clean.** Метка — `zone: vision`, а правило clean (§14.9) vision не блокирует: чистоту решает детерминированная часть, метка человека — задание «чини дословно» для этого прохода. Если боевой прогон покажет, что метку нужно считать блокирующей (иначе итерацию можно закрыть чистой при неисправленной метке), это одна строка в `state.is_blocking` — решать после X.4.

**Не проверено данными.** Работа мышью в других браузерах (проверен Chromium; тач-экраны — `touch-action:none` без проверки), длинные экраны с десятками меток (пины и карточки), точность пинов макета при `frameBox` и масштабе картинки дизайна, большой снимок (боксы вшиваются в страницу: 4000 × ~50 байт), то, как человек реально кладёт скачанный файл (путь из текста страницы — подсказка, не проверка), слабая модель, читающая сводку `decisions` из ответа.
