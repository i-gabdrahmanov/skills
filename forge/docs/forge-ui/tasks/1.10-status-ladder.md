# 1.10 — daiver_status: лестница трека и предупреждения

**Этап:** 1 · **Зависит от:** 1.9, 1.8 · **Статус:** done
**Спека:** §3.2 (лестница), §15.7 (статус и предупреждения) · **INV:** C1, A13 · **QG:** S2, X4

## Зачем
Первый ход агента — `daiver_status`; какая ступень у трека и что делать дальше, решает код по
артефактам на диске, а не модель листанием `.daiver/`.

## Что сделать
Расширить `daiver/status.py`:
- Ступень кадра: empty → requirement → normalized (канон) → planned (plan.json) → building
  (build-state с pending/stale) → built (всё done или записаны sources) → verifying (итерации и
  открытые blocking) → clean (последняя итерация чистая). `building` проверяется РАНЬШЕ ступеней
  verify — стухшая секция возвращает проверенный трек в сборку.
- Трек: ступень фронтирного кадра (первого с работой в порядке манифеста); clean ⇔ все кадры clean;
  битый state-файл читается как отсутствующий (и называется в warnings), а не роняет статус.
- `nextStep` — шаг forge (`ui-design`/`ui-build`/`ui-verify`) с именем кадра.
- Предупреждения вслух: требование устарело (sha256 ≠, громче всего у собранного кадра без
  версии), нет goal image, арт без `.svg`, требования ДС не строились (stories/sources), кадр без
  требования, URL не записан после built, спеки не на месте, pull без frameUrl.

## Готово, когда
- `test_status_ladder.py`: табличный тест по сочетаниям артефактов → ожидаемые stage/nextStep
  (S2), включая «stale после verify → building» и битый state-файл.

## Результат
`daiver/status.py` (лестница, предупреждения, ответ), `track.implementation_url` (адрес страницы по ролям), в `tools.py` — общий
`_story_spec_path` (путь ui-spec.md стори для `daiver_spec` и статуса) и резолвер, который `daiver_status`/`daiver_init` передают в статус,
`test_status_ladder.py` (51 тест). Мутационно проверено 30 правил в копии дерева — все пойманы (мутант «статус пишет на диск» сначала
выжил: создавал уже существующий каталог; усилен записью файла и пойман тестом «статус только читает»).
- **Данные образца.** «Modal» после `daiver_pixso_pull` — ступень `requirement`, после `daiver_normalize` — `normalized`; единственное
  предупреждение — `goal-image-missing` (арта в каноне образца нет, `canonical-stale` молчит: `stats.sourceSha256` равен
  `requirement.sha256` манифеста); растр через `rasterPath` его гасит. Выше лестницу поднимают синтетические state-файлы (писателей
  нет): planned → building → built → verifying → clean; тронутый мимо pull файл требования у собранного кадра без `versions/` даёт
  `requirement-stale-built` первым в списке, ступень clean при этом не понижается (`SampleFlow`).
- **Лестница.** `empty → requirement → normalized → planned → building → built → verifying → clean`; ступень кадра — САМАЯ ВЫСОКАЯ из
  подряд достигнутых (чистая функция `stage_of(facts)`): артефакт выше пропавшего нижнего не учитывается — канон пропал у чистого кадра
  → `requirement` и nextStep `daiver_normalize`, вернулся тот же файл → снова clean (самолечение, пин). `building` — раньше verify:
  `stale`/`pending`/`in_progress` после чистой истории возвращают кадр в сборку (пин «stale после verify → building» и сценарий
  clean → stale → clean). Устаревшее требование ступень НЕ понижает (предупреждение), пропавший файл требования — понижает до `empty`.
- **Минимальный контракт артефактов, которых ещё нет как кода** (имена файлов — из `track.frame_paths`): `plan.json` — JSON-объект
  (наличие и разбираемость, содержимое не читается); `build-state.json` — `sections[]` непустой список, у каждой `status` ∈
  pending|in_progress|done|stale; `verify-state.json` — `history[]` (пустой допустим = итерация открыта, ступень built), у последней
  записи `clean` — bool, `blocking` — число или список (необязательно, только для текста). Всё прочее (не UTF-8, не JSON, не тот тип,
  статус вне перечня, пустой `sections`, JSON глубже рекурсии, JSON `null`) читается как ОТСУТСТВУЮЩЕЕ, называется в warnings
  (`artifact-unreadable`, имя файла и причина) и не роняет статус; директория на месте файла — просто нет файла. Строка-примечание об
  этом контракте добавлена в задачи 2.6, 3.1, 4.8.
- **Трек.** Ступень трека — ступень фронтирного кадра (первый не-clean в порядке манифеста, не по алфавиту и не по высоте ступени); clean
  ⇔ все кадры clean; в `nextStep` трека — шаг фронтира и хвост «Далее по треку: b (planned), d (empty)». `outcome` — функция ступеней
  (пин на всех парах ступеней, X4): `clean` — все кадры clean; `defects-remaining` — есть кадр в verifying; иначе `never-run` (в том числе
  смешанный трек и кадр, стухший после verify: его проверка относилась к прежней сборке). `blocked:<причина>` и `run.json` — 7.1.
- **nextStep.** `<ui-design|ui-build|ui-verify>: кадр «имя» трека T — что делать`; clean — «готово: …». Имена шагов сверены с реестром
  ветки (`hooks/_branches.py` → `forgeui`, пин). Текст ступени называет только инструменты, существующие к ней (`daiver_pixso_pull`,
  `daiver_normalize`, `daiver_outline`; `daiver_build_state` — только на `building`, недостижимой без файла его писателя; на `built`
  инструмента verify нет в тексте — к этой ступени его может ещё не быть).
  Верхний `nextStep` — как в каркасе (`init:` / `ui-spec:`), а при треках — nextStep первого незавершённого трека по имени + «Если твоя
  стори — другая (её ключа нет среди tracks[]), начни с ui-spec»; у каждого трека свой `nextStep`. Аргумента `track` у инструмента нет
  (сигнатура Этапа 0 сохранена; неизвестный аргумент по-прежнему отказ).
- **Ответ.** Ключи: `engine, initialized, config, designSystem, problems, warnings, tracks, nextStep`. `tracks` — теперь список объектов
  (Этап 0 отдавал имена; потребителей списка имён в коде не было): `{name, stage, outcome, frame?, nextStep, frames[]}`, кадр —
  `{name, role, stage, dir, stateOf?, url?, requirement?, requirementStatus?, goalImage, build? "k/n", iterations?, blocking?}`.
  `designSystem` — `{source, requirements: built | missing | not-needed}` (null до init). Ответ плоский: однокадровый трек ≈ 32 строки в
  `indent=1`, четыре кадра с предупреждением ≈ 70 (пин: < 50 и < 110). Детерминирован (два одинаковых дерева → побайтно один ответ, без
  путей temp и времени) и только читает (снимок дерева до/после совпадает).
- **Предупреждения** — строки `<код>: <текст>` в `warnings` (после строк конфига; громкие первыми): `requirement-stale-built` (хеш не совпал, у
  кадра есть `build-state.json` — «собран» как у pull — и нет подкаталога `versions/`), `requirement-stale`, `requirement-missing`,
  `frame-no-requirement`, `frame-url-missing` (pull без frameUrl), `goal-image-missing` (не записана / файла нет / не PNG-JPEG; как её
  видит `track.raster_info` — положенный руками файл без `rasterPath` не считается), `art-svg-missing` (`svg_assets.load_arts` +
  `missing_slugs`, с ступени normalized, occluded-арты молчат), `implementation-url-missing` (только на ступени built),
  `specs-missing` (те же пути, что собирает `daiver_spec`: ui-spec.md стори + `specs[]` манифеста; путь стори определяет хост-резолвер,
  без него — только `specs[]`), `ds-requirements-missing` (только `library.source` stories|sources: нет одного из двух файлов
  `.daiver/design-system-requirements{,.details}.json`); служебные — `artifact-unreadable`, `canonical-stale`, `manifest-unreadable`
  (повреждённый track.yaml: трек пуст и назван, соседние треки живы). Тест `test_every_warning_code_is_reachable` поднимает все 13 кодов
  одним репо.
- **Адрес страницы по ролям** (`track.implementation_url`, 4.9 берёт готовое): `frames[].url`; первичный кадр → `implementation.url`
  трека; состояние → адрес своего экрана (свой url экрана или url трека у первичного); диалог не наследует никогда (в том числе будучи
  первичным); второй экран не наследует.
- **Отклонения (строки в README):** «записаны sources» ступень не повышает; поля requirement/goal image/build/verify — у кадра, а не у трека.
- **Не проверено данными (допущения).** Форматы `plan.json`, `build-state.json`, `verify-state.json` — наш минимум по тексту спеки и
  задач 2.6/3.1/4.8; писателей нет, сверить при их появлении (строки-примечания лежат в этих задачах). Решение `stop` в verify-state
  статус не читает: остановленный кадр остаётся verifying с `defects-remaining`. Рассинхрон `plan.json` ↔ `build-state.json` (план
  перегенерирован, секции не сверены) лестница не видит — сверка хешей секций дело `daiver_build_state` (3.1). Кадры, объявленные в
  таблице «Кадры» ui-spec.md, но не заведённые в трек, статус не сверяет (имена в таблице свободные, имя кадра трека — каталог):
  полнота кадров — проверка `requirement` контракта плана (2.6). Правило адреса для роли breakpoint в спеке не названо — не наследует.
  Текст `ds-requirements-missing` не называет инструмента (`daiver_ds_requirements` появится в 2.2) — имя дописать там. Как слабая
  модель читает длину и формулировки ответа — проба боевого прогона (X.4).
