# 6.3 — Ревизии макета (versions)

**Этап:** 6 · **Зависит от:** 6.1 · **Статус:** done
**Спека:** §7.3 (pull поверх собранного), §13.7 (version), §10.1 (кандидаты изменения), §14.4.6
(baseline.verdict) · **INV:** B15, G3, C18 · **QG:** U22 (часть), P2

## Зачем
Дизайнер поменял макет уже собранного экрана: это ИЗМЕНЕНИЕ, которое строится внутрь
существующего кода читаемым диффом, а не новый экран рядом.

## Что сделать
- Pull поверх СОБРАННОГО кадра: вся семья уходит в `versions/<n>/` (целиком, не удаляется
  никогда), база записывается, подпись плана протухает (lock меняется), растр уходит с версией;
  ответ — `mode:"revision"` + схожесть регионов; несобранный кадр перезаписывается как раньше;
  кадр-состояние не трогается.
- Инструмент **`daiver_frame_baseline(track, frame)`**: регионы против прошлой версии, у каждого —
  файлы, куда он был построен (из старого плана/build-state); `daiver_section` отдаёт дельту с
  блоком `baseline` (shared-стабы по base-id, added, removed, changed, wraps); хеш региона = хеш
  дельты (третий pull переоткроет только сдвинутые регионы).
- Резолв: shared-узел наследует вердикт старого плана по base-id; кандидаты — только в изменённом.
- Сборка в существующий код: added — пишутся, removed — УДАЛЯЮТСЯ (сказать, если ещё кто-то
  использует), changed — правятся на месте, wraps — обёртка/разворачивание; ни пролога, ни нового
  модуля/маршрута/моков с нуля; структура, имена и стиль сохраняются.
- Verify: `baseline.verdict` current (обычный ход) / previous (не hard gate: MISSING/EXTRA — само
  изменение; проверить сервер перед фиксами) / ambiguous / unknown; код-гейт сканирует файлы каждой
  версии.

## Готово, когда
- `test_revisions.py`: второй pull изменённой фикстуры — `versions/1` полностью, подпись stale,
  дельты регионов, build-state переоткрывает только изменённые регионы, четыре вердикта базы.

*Заметка (3.1).* Правило pull «есть `build-state.json` — кадр собран, отказ» (1.2/1.10) теперь запирает кадр уже после первого `daiver_build_state` (все секции pending): стухание через повторный pull достижимо только после того, как
эта задача смягчит правило (например, «есть секция `done`» вместо «файл есть» — и то же в предупреждении `requirement-stale-built` лестницы) и решит судьбу state-файла при ревизии (`versions/<n>/`). Состояние хранит
`outputs` каждой секции — «файлы, куда регион был построен». Пин текущего поведения — `test_build_state.ModalSample` (его придётся обновить вместе с правилом).

## Сделано

Инструмент **`daiver_frame_baseline(track, frame)`** (читающий, свободный на любом шаге). Код: `daiver/baseline.py` (увод семьи в версию, регионы против собранной версии и их файлы, унаследованные вердикты, вердикт базы, секции всех версий для гейтов), `pixso/pull.py` (ревизия), `track.py` (поля `versions`, `baseline`, `version_paths`), `status.py` (`frame_built` — одно правило «собран» для pull и лестницы), `outline.py` (`_load` подменяет корень ревизии дельта-корнем, блок `baseline` в outline и section), `resolve.py` (хранилище версии — ранний эталон, подсказка `baseVerdict`), `plan.py` / `plan_digest.py` / `plan_contract.py` (`plan.baseline`, раздел «Изменение версии», «Ревизии», пункт `baseline`), `build_state.py` (`revision.removed`), `verify/verify_compare.py`, `verify/code_compare.py`, `verify/ds_gate.py`. Тесты: `test_revisions.py` (**39**); переписаны пины старого правила pull (`test_build_state.ModalSample`, `test_pixso_pull`, `test_status_ladder` — «собран» теперь «все секции done»).

- **Pull поверх собранного** (все секции build-state `done`): семья кадра целиком — требование и сырой экспорт, растр, канон, арты, план, резолвы, build-state, verify-state, `verify/`, `baseline/` — уходит переименованием в `versions/<n>/` (байт в байт, не удаляется никогда; каталог, которого манифест не знает, не затирается — номер следующий свободный). Манифест: `versions [{n, requirement, retiredAt, raster?, frameBox?}]` и `baseline {kind: version, version}`; растр и рамка кадра уходят с версией; оба поля пишет только pull (`daiver_track_manifest` их не правит). Подпись слетает сама (плана кадра больше нет, хеш требования другой). Ответ — `mode: revision`, `version`, `revision {moved, similarity, regions}` (канон новой версии — в памяти) и строка «REVISION — …». Недостроенный кадр перезаписывается (`mode: overwrite`), кадр-состояние не версионируется никогда, тот же экспорт — `mode: unchanged`, повреждённый build-state и несоздаваемый каталог версии — отказ без следов (увод обратим до записи манифеста).
- **Регионы** — то же сравнение, что у кадра-состояния, без гейта схожести (низкая — предупреждение «почти целиком другая»): shared / added / removed / changed, у каждого `files` — куда построен в коде (outputs секций базы, которые содержат узел или лежат в нём; через цепочку версий, если база сама ревизия; у added — файлы родителя). Дельта-корень `inferred:delta:<кадр>@v<n>`: outline (секции — регионы added и changed, блок `baseline` с удаляемым), section (`baseline.region` + `files`, бриф «правь существующие файлы, ни пролога»), резолв (кандидаты только в регионах), план и build-state идут по нему. Хеш региона = хеш дельты: повторный pull недостроенной ревизии переоткрывает только подвинутый регион.
- **Резолв**: хранилище собранной версии — самый ранний эталон переиспользования (узел с тем же figmaName и вариантами получает вердикт версии копией, «кадр» `<имя> v<n>`); changed-узел со сменённым вариантом — кандидат с подсказкой `baseVerdict`. **План**: `baseline {version, similarity, removed [с файлами], inherited [решения shared-частей по base-id]}`, `plan.md` — «Изменение версии» (без пролога и оболочки), `ui-plan.md` — «Ревизии», строка в вопросе подписи; место корня не-первичного кадра по умолчанию — у версии. Контракт: пункт `baseline` ok у ревизии и блокирует, если канона версии нет.
- **Сборка**: секции — только изменённое; `daiver_build_state` называет `revision.removed` (удалить из кода); бриф ui-build — без пролога, правка файлов региона, удаление с проверкой чужих потребителей. **Verify**: `baseline.verdict` current / previous / ambiguous / unknown (свидетели — как у состояния); `previous` — не жёсткий гейт, nextStep — сначала проверить свежесть сборки сервера; код-гейт и DS-гейт сканируют файлы каждой версии (секции ревизии сливаются с секциями версии по id и общему файлу). Попутно: инстанс с изменённым лишь текстом слота больше не свидетель вердикта (и у состояния 6.2) — матчер спаривает его по имени на странице любой стороны.
- **Мутационная проверка** (одноразовый скрипт, байткод — во временный каталог): 36 мутантов (правило «собран», ревизия/перезапись/состояние, состав семьи, растр, номер версии, файлы по поддереву и по цепочке, файлы added, наследование, вердикт и его предупреждение, слияние секций, свидетель слота, гейт схожести, вердикт в compare и nextStep, файлы части региона, дельта-корень, эталон версии и подсказка резолва, место корня, inherited в плане и DS-гейте, оболочка в plan.md, файлы версий в код- и DS-гейте, ответ build-state, пункт контракта, проверки манифеста) — убиты все. Первый прогон показал дыру «файлы региона по поддереву» — дописан тест.

**Не проверено данными.** Сохраняет ли Pixso id узлов между ревизиями, размер дельты на живой правке, точность `files` на модуле, где файл держит несколько секций или оболочку, как слабая модель правит существующий код и удаляет `removed`, `previous` против горячей перезагрузки dev-сервера (README → «Нужно от пользователя»).
