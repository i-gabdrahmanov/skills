# 6.3 — Ревизии макета (versions)

**Этап:** 6 · **Зависит от:** 6.1 · **Статус:** todo
**Спека:** §7.3 (pull поверх собранного), §13.7 (version), §10.1 (кандидаты изменения), §14.4.6
(baseline.verdict) · **INV:** B15, G3, C18 · **QG:** U22 (часть), P2

## Зачем
Дизайнер поменял макет уже собранного экрана: это ИЗМЕНЕНИЕ, которое строится внутрь
существующего кода читаемым диффом, а не новый экран рядом.

## Что сделать
- Pull поверх СОБРАННОГО кадра: вся семья уходит в `versions/<n>/` (целиком, не удаляется
  никогда), база записывается, подпись плана протухает (lock меняется), растр уходит с версией;
  ответ — `mode:"revision"` + схожесть регионов; несобранный кадр перезаписывается как раньше;
  кадр-состояние не трогается.
- Инструмент **`daiver_frame_baseline(track, frame)`**: регионы против прошлой версии, у каждого —
  файлы, куда он был построен (из старого плана/build-state); `daiver_section` отдаёт дельту с
  блоком `baseline` (shared-стабы по base-id, added, removed, changed, wraps); хеш региона = хеш
  дельты (третий pull переоткроет только сдвинутые регионы).
- Резолв: shared-узел наследует вердикт старого плана по base-id; кандидаты — только в изменённом.
- Сборка в существующий код: added — пишутся, removed — УДАЛЯЮТСЯ (сказать, если ещё кто-то
  использует), changed — правятся на месте, wraps — обёртка/разворачивание; ни пролога, ни нового
  модуля/маршрута/моков с нуля; структура, имена и стиль сохраняются.
- Verify: `baseline.verdict` current (обычный ход) / previous (не hard gate: MISSING/EXTRA — само
  изменение; проверить сервер перед фиксами) / ambiguous / unknown; код-гейт сканирует файлы каждой
  версии.

## Готово, когда
- `test_revisions.py`: второй pull изменённой фикстуры — `versions/1` полностью, подпись stale,
  дельты регионов, build-state переоткрывает только изменённые регионы, четыре вердикта базы.

*Заметка (3.1).* Правило pull «есть `build-state.json` — кадр собран, отказ» (1.2/1.10) теперь запирает кадр уже после первого `daiver_build_state` (все секции pending): стухание через повторный pull достижимо только после того, как
эта задача смягчит правило (например, «есть секция `done`» вместо «файл есть» — и то же в предупреждении `requirement-stale-built` лестницы) и решит судьбу state-файла при ревизии (`versions/<n>/`). Состояние хранит
`outputs` каждой секции — «файлы, куда регион был построен». Пин текущего поведения — `test_build_state.ModalSample` (его придётся обновить вместе с правилом).
