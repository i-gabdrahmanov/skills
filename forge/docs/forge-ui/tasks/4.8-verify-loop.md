# 4.8 — Цикл verify: состояние, запись, решения, verify-report.md, шаг ui-verify

**Этап:** 4 · **Зависит от:** 4.6, 4.7 · **Статус:** done
**Спека:** §14.1, §14.2, §14.9, §14.11, §14.13 · **INV:** C21, C24, C25, C33, C34, C35, G4, G11, F12,
F15 · **QG:** U14, P6 (часть)

## Зачем
Цикл заканчивает пользователь: чисто или стоп. Память цикла — на диске, номера итераций в голове не
считаются, решения человека исполняются дословно.

## Что сделать
- `daiver/verify/state.py`; инструменты:
  - **`daiver_verify_state(track, frame?)`** — открывает итерацию: номер, `iterationDir`
    (`verify/iter-N/`, не перезаписывается), `priorReview` (Fix plan прошлой или null), `goalImage`,
    `missingArt`, `warnStalling` (с `warnAfterVerifyIterations`), `history`, `implementation`
    (url/open/devCommand, 4.9), `mode`; итерация исполнена, но не записана → `unrecordedIterations`
    и инструкция записать СЕЙЧАС; повтор до записи номер не двигает.
  - **`daiver_verify_state_record(track, frame?, iteration, gates{compare, code, visualDiff, review,
    e2e}, diffPercent, reviewReport?, reviewSkipped?, defects, decision?, fixed?, declined?)`** →
    `clean`, `blocking`, `progress` (`stalled`: не лучше прошлой; регресс — тоже stall). Ровно пять
    имён гейтов; `diffPercent` — проценты 0–100, как вернул дифф.
  - Правило clean: блокируют только не-noise Critical/Major из deterministic-зон; vision — никогда;
    pre-existing (scope change) — нет; регрессия — да; hard gate fail — не clean; любой другой
    failed-гейт — не clean; skipped e2e/review — не мешает; code fail — блокирует, skip — нет.
- `verify-decisions.json` (разбор): версия схемы (чужую — отказ); решение замораживает снимок
  дефекта (значения сдвинулись → REOPENED с заметкой); переформулировка сама не переоткрывает;
  неизвестные id названы; reviewer переносится; пустая note не переносится; файл одного кадра в его
  папке, позже `decidedAt` выигрывает.
- `verify-report.md` — один на трек: frontmatter outcome (`track, outcome clean|defects-remaining,
  iterations, defectsRemaining, mode, frames{}`), `## frame:` по истории: статусы гейтов, matchRate,
  diff %, вердикт обзора, фиксы и отказы, ссылка на report.html, непрогнанные гейты и почему, всё
  нерешённое, кто закончил цикл; непроверенные кадры названы.
- `ui_gate.py verify`: последняя записанная итерация clean ИЛИ решение stop при согласии
  `ui-accept-<KEY>` (итог defects-remaining честно в отчёте).
- Бриф `ui-verify`: итерация = state → screenshot → compare (hard) → code → [дифф → обзор → e2e] →
  record → путь отчёта пользователю → вопрос через `pending_questions`: clean — готово; иначе
  блокирующие пункты (severity, задуманный фикс, file:line, прогресс, FIXED/NOT FIXED/REGRESSED,
  warnStalling, отклонённые раньше — не переспрашивать) → «чинить всё / пункты / стоп». Фикс —
  переоткрытие `ui-build` с согласованными пунктами дословно; стоп — сразу, без «последней правки».
- **Контракт для статуса (1.10):** лестница `daiver_status` читает `verify-state.json` → `history[]` (пустой список допустим), у последней записи `clean` (bool, обязателен) и `blocking` (число или список, необязателен); clean ⇔ последняя запись чистая и все секции `done` — не ломать.

## Готово, когда
- `test_verify_state.py`: нумерация и `unrecordedIterations`; повтор до записи идемпотентен; матрица
  правила clean; инварианты файла решений; формат verify-report.md; гейт verify (clean / stop с
  согласием / без согласия — нет).

*Заметка (3.3).* `ui-guard` отказывает на любую запись кода в `project.outputDir` вне шага `ui-build`; отказ на `ui-verify` называет путь: `python3 <harness>/skills/pipeline-state/scripts/update.py --skill forgeui
--feature <KEY> --step-id ui-build --status pending`. Бриф `ui-verify` должен вести фикс именно так (переоткрытие после решения человека), а не правкой на ходу; переоткрытый `ui-build` пускает запись, если подпись плана
действительна (иначе субагент возвращает `failed`: план менялся). Файлы итерации (`verify/**`, отчёты) лежат в `.daiver/` — хук их не трогает.

*Заметка (3.4).* `state-write-guard` охраняет `verify/**`, `**/verify-state.json`, `versions/**`, `baseline/**`, `run.json`; `daiver_verify_*` — в `phase_tools` шага `ui-verify` (ГЛАВНЫЙ агент их не вызывает). НЕ охраняются файлы этой
задачи, которых в списке 3.4 не было: `verify-report.md` (один на трек), `verify-decisions.json` и `report.html` — добавить их шаблоны в `_DAIVER_PATTERNS` (`hooks/state-write-guard.py`) и тест в `test_state-write-guard.py`, КРОМЕ того,
что кладёт человек (`verify-decisions.json` скачивается из отчёта и ложится руками — если его будет класть модель, решить, кто пишет). Какие из `daiver_verify_*` оркестратор вызывает сам (показать путь отчёта, «чинить/стоп»), а какие — субагент
итерации: те, что зовёт оркестратор, исключить из шаблона `daiver_verify_*` (шаблон придётся заменить именами).

*Заметка (4.1).* Первый ход итерации (до `daiver_verify_state`) — `daiver_capabilities`: `ready: false` → цикл не стартует, ответ уже содержит `blocked: no-browser`, `supply` и запрет ставить браузер; `warnings` (старый
браузер, битые `verify.browser*`) ретранслируются человеку. `vision.enabled: false` (`verify.vision: off`) — гейт визуального обзора записывает `skipped` код, а не модель. `playwright.found` — вход e2e-гейта (5.5).

## Результат
Память цикла verify на диске и замыкание цикла. Три инструмента: **`daiver_verify_state`** (открыть итерацию), **`daiver_verify_state_record`** (записать итог итерации), **`daiver_verify_decide`** (решение человека; вне `phase_tools` — его зовёт оркестратор). Модули `verify/{state,decisions,verify_report,verify_gate}.py`; `ui_gate.py verify` теперь настоящий гейт (был exit 3); бриф `ui-verify` (§5 `SKILL.md`) написан для живых гейтов; `state-write-guard` закрыл `verify-report.md`, `verify-decisions.json`, `report.html`. Тесты: `test_verify_state.py` (**50**), правки `test_ui_gate_build.py`, `test_plan_contract.py`, `test_resolution_report.py` (verify: exit 1 вместо 3), `test_state-write-guard.py`, реестры хуков.

- **`daiver_verify_state`**: `iteration` и `iterationDir` (`verify/iter-N/`, не пересоздаётся), `unrecordedIterations` (исполнена, не записана → записать СЕЙЧАС; повтор до записи номер не двигает), `priorReview`, `goalImage` (нет на 1-й итерации — warning «спроси человека»), `missingArt`, `warnStalling` (после `warnAfterVerifyIterations` и не чисто), `history`, `implementation {url, open, devCommand, need?}` (то, что даёт манифест; URL и dev-сервер — 4.9), `declinedSoFar`, `mode`, `maxVerifyIterations`, `decisions {sources, problems}`.
- **`daiver_verify_state_record`** не доверяет словам агента там, где у движка есть факт (принцип 3): статусы `compare` и `code`, `matchRate`, `fidelity` и ВСЕ дефекты берутся из `compare-summary.json` / `code-summary.json` / `defects.json` / `code-defects.json` папки итерации (измеренное выигрывает у кода по общему id), расхождение слов с фактом — `warnings`; агент даёт то, чего движок не знает: `visualDiff` / `review` / `e2e` (до этапа 5 — `skipped` с причиной), `diffPercent` (0–100), пункты vision/e2e в `defects` (другие зоны отказ). Ровно пять гейтов; итерация должна иметь следы исполнения; повторная запись и запись «в прошлое» отказаны. Результат: `clean`, `blocking`, `progress` (`stalled`: не лучше прошлой; регресс — тоже), путь `verify-report.md`.
- **Правило clean** (§14.9) — матрица тестов: блокируют critical/major без noise из зоны deterministic; vision не блокирует; pre-existing (`standing`) нет; регрессия да; hard gate / перезахват / compare не исполнялся — не clean даже без дефектов; любой другой `fail` — не clean; skipped/degraded e2e, review — не мешают; code fail блокирует (если остались блокирующие дефекты кода, иначе `pass`), skip нет. `decision: clean` на нечистой итерации отказан.
- **`verify-decisions.json`** (`decisions.py`): схема 1 (чужая — отказ), `fix | skip | false_positive`; снимок дефекта заморожен (`snapshot.rows`; значения уехали → `reopened` с заметкой, переформулировка не переоткрывает); skip → declined (остаётся блокирующим, не переспрашивается); false_positive → noise с reviewer; пустая заметка не переносится; неизвестные id и негодные записи названы; `frame` другого кадра — `elsewhere`; файл трека и файл кадра сливаются по «позже `decidedAt`», при равных кадр сильнее. Файл кладёт ЧЕЛОВЕК — хук закрывает путь модели. Теперь его читает и `daiver_verify_compare` (прежнее временное `verify/decisions.json` из 4.6 убрано).
- **`verify-report.md`** (один на трек; пишет движок из `verify-state.json` при каждой записи и решении, детерминирован): frontmatter `track, outcome, iterations, defectsRemaining, mode, frames{}` (при нескольких кадрах); `## frame:` по итерациям (гейты, matchRate/fidelity, diff %, обзор, блокирующие/застой, исправлено/отклонено, решение, ссылка на report.html, если файл есть); итог кадра — не исполнявшиеся гейты и почему, нерешённое из последней записи (minor / noise / declined / vision / pre-existing с пометками), кто закончил цикл; непроверенные кадры названы, outcome с ними — `defects-remaining`.
- **Гейт `ui_gate.py verify`**: у каждого кадра последняя запись `clean` ИЛИ `decision: stop` при согласии `ui-accept-<KEY>`; кадр без записей, повреждённый `verify-state.json`, нечистая итерация без решения «стоп», стоп без согласия — шаг не закрыт (exit 1 с причинами). Контракт лестницы `daiver_status` (1.10) не нарушен: `history[-1].clean` (bool) и `blocking` (список) пишутся как раньше.
- **Мутационная проверка** (одноразовый скрипт): 38 мутантов (номера и `unrecorded`, пять гейтов, проценты, слова агента против факта, vision/noise/pre-existing/minor, compare не исполнялся, failed-гейты, code fail, измеренное против кода, stall по регрессу и по равенству, отказ clean/decide/повторной записи, порядок истории, зоны, warnStalling, схема решений, снимок, skip/false_positive, заметка, reviewer, unknown, elsewhere, «позже выигрывает», итог отчёта, карта кадров, согласие, ссылка на html, гейт) — убиты все, кроме эквивалентного «ничья по рангу» (при разном ранге `>` и `>=` совпадают).

**Не проверено данными.** Боевых итераций нет: порог stall («не лучше» по числу блокирующих; регресс — тоже); как слабая модель читает `unrecordedIterations`, `warnStalling` и разделение «субагент пишет итерацию — оркестратор записывает решение»; форма `reviewReport` (закрепит 5.2) и `diffPercent` реального диффа; заморозка снимка в отчёте (5.3–5.4 должны класть `DEC.snapshot_of(defect)` в решение); автономный триаж и `capReached` — 7.2; режим и `report.html` из run-рекорда — 7.1 / 5.3.
