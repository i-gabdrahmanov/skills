# 2.6 — План секций, контракт готовности, подпись

**Этап:** 2 · **Зависит от:** 2.5 · **Статус:** done
**Спека:** §11.5–11.6, §12.2–12.4, §20.4 (16 id проверок контракта) · **INV:** B12, C8, C9, D1, F6 ·
**QG:** U12

## Зачем
План — контракт для сборки; человек подписывает ровно прочитанное, а подпись умирает при смене
требования. Всё, что автономная сборка спросила бы, выясняется сейчас.

## Что сделать
- `daiver/plan.py` + инструмент **`daiver_plan_write(track, frame, plan)`** (отклонение от спеки:
  план пишет инструмент с валидацией, а не модель файлом — INV-A11): дерево секций; на узел
  `{component, props}` | `{resolution:"local"}` | `{resolution:"ignore"}`; у контейнеров дайджест
  раскладки из outline; ссылки на разделы спеки; `buildOrder` — РЕАЛЬНЫЕ id секций с хешами
  (сначала секции с общими local-компонентами, потом потребители, потом порядок документа;
  пролог — не секция). Пишет `plan.json` и человекочитаемый `plan.md`.
- **`daiver_plan_contract(track)`** — из ДИСКА: проверки `initialized, library-source, browser,
  requirement, canonical, plan, resolutions, assets, goal-image, specs, state, baseline, sources,
  implementation, dev-command, signature`, у каждой `{id, frame?, blocking, blockedReason, owner
  human|plan|host, detail, ask (дословный вопрос), degradesTo}`; `ready` (нет блокирующих),
  `complete` (нет и деградаций), `signed`; `planUncertainty` — каждый узел один раз; неразбираемый
  план ≠ pass.
- `ui-plan.md` — дайджест для ревьюера: кадры / секции / компоненты (+ local и почему) /
  дизайн-система (токены, несовпавшие цвета) / ассеты (+ плейсхолдеры) / бизнес-логика (спеки →
  e2e) / принятые деградации / открытые вопросы. Каждый факт — из артефакта.
- `plan.lock.json` — sha256 требований, `plan.json`, `resolution-report.md`, `ui-plan.md`. Подпись:
  `record_approval.py --key ui-plan-<KEY> --bind-file .daiver/tracks/<KEY>/plan.lock.json --evidence
  "<ответ>"`; `signed` = согласие есть и `bound_sha256` = текущему lock; re-pull → lock меняется →
  подпись stale.
- Brownfield-вопросы шага: url/open кадра, devCommand, sources, scope, baseline — в контракт как
  `ask`, ответы — `daiver_track_manifest`.
- `ui_gate.py design` по-настоящему: контракт `ready`, lock есть, подпись валидна.
- **Контракт для статуса (1.10):** лестница `daiver_status` читает у `plan.json` лишь наличие и разбираемость (JSON-объект), содержимое не читает — не ломать; неразбираемый план статус считает отсутствующим и называет в warnings (`artifact-unreadable`).

## Готово, когда
- `test_plan_contract.py`: матрица проверок контракта; неверный buildOrder (чужой id, хеш не тот)
  — отказ `plan_write`; подпись stale после re-pull; гейт design: 0 только при ready+signed.

*Заметка-контракт (2.5).* `resolution-report.md` пишет `daiver_resolve_report` (детерминирован — его sha256 годится для lock). Проверка резолва —
`resolution_report.check(root, track)`: пусто = всё решено, отчёт актуален, вердикты, которые обязан увидеть человек, подтверждены согласием
`ui-resolve-<KEY>` на этот отчёт; проверка контракта `resolutions` зовёт её, `ui_gate.py design` уже зовёт (не готово — exit 1, готово — exit 3 до плана): здесь
добавляются план и подпись, а exit 0 появляется только при них. Вердикты для плана — `resolve.verdicts(root, track, frame)` после `daiver_resolve_report`
(он раздаёт эталоны между кадрами). Решения layoutHints шага ui-design нигде не сохранены — их место в плане (контейнеры из `unproven` outline, §11.4).
Полнота кадров относительно таблицы «Кадры» `ui-spec.md` в гейте 2.5 не проверяется — это check `requirement` контракта.

## Результат
Три модуля движка: `daiver/plan.py` (plan.json и plan.md кадра: сборка плана из данных, проверка входа модели и её `buildOrder`, решения по раскладке, пересборка-сверка),
`daiver/plan_contract.py` (16 проверок, подпись, lock, `planUncertainty`, `evaluate` / `run` / `gate_problems` / `signature_state`) и `daiver/plan_digest.py` (`ui-plan.md`). В `tools.py` —
два инструмента: **`daiver_plan_write(track, frame?, plan?, weightBudget?)`** (новый сверх списка спеки — строка README) и **`daiver_plan_contract(track)`** (оба — в `EXPECTED_TOOLS`); в `track.py` —
поля кадра `sources` и `scope`; `ui_gate.py design` теперь возвращает 0; бриф `SKILL.md` §3 (10 пунктов: планы кадров → контракт → вопросы → подпись → гейт через раннер) и §3.1 (виды вопросов
`plan-question` и `sign-plan`, запись согласия `ui-plan-<KEY>`); `FORGE.md`. Тесты: `test_plan_contract.py` (141: матрица 16 проверок, запись и проверка плана, порядок сборки, подпись и
lock, гейт, неопределённость, дайджест, несколько кадров, гигиена модулей), правки `test_ui_design_brief.py` (16: +1), `test_resolution_report.py` (гейт больше не отвечает exit 3), `test_track_manifest.py`
(33: +3), `hooks/test_daiver_mcp.py`. Мутационно проверено 82 правила (одноразовый скрипт: копия дерева, правка текста модуля): 6 выжили с первого прогона (ключи плана не
отсортированы; неуверенность считалась только по low; подпись без сверки хеша и подпись по lock с диска, а не по собранному — обоих закрывала проверка файлов на диске, поэтому тест теперь
проверяет ПРИЧИНУ; ключ согласия без ключа стори; снятие согласия у неготового плана) и получили тесты, три не применились из-за устаревшего фрагмента — исправлены; итог 82/82.

- **Данные образца.** «Modal» целиком — ОДНА секция (корень `2:153702`, `hash` `0ccf768ee9d7`, 3101 Б; так при бюджете по умолчанию и любом ≥ 3101), оболочки над секциями нет, `buildOrder` из одной
  записи, `unproven` пуст, общих local-компонентов нет; четыре кандидата — три строки таблицы `plan.md` (два «Modal Header» — одна строка «×2»). `plan.json` 3117 Б, `plan.md` 2602 Б, `ui-plan.md` 3825 Б,
  `plan.lock.json` 439 Б. Золотой `plan.md` — `GOLDEN_MODAL_PLAN_MD` в `test_plan_contract.py` (единственное место, где формат зафиксирован целиком). Перетяжка того же экспорта ничего не меняет, перетяжка
  экспорта с изменённым текстом слота сбрасывает подпись: sha256 требования другой, pull удалил канон, план `stale`; после пересборки плана прежнее согласие снимает `daiver_plan_contract`, подписывают заново.
- **План пишет код.** Модель называет только то, чего в данных нет: `plan.layout` (решение по КАЖДОЙ записи `unproven` — §11.4), `plan.layoutRest: "keep-px"` («остальное остаётся px без свидетельства») и,
  если хочет, свой `buildOrder`, который код СВЕРЯЕТ: чужой id, пролог как шаг, не тот хеш, пропущенная или дважды названная секция, occluded, не тот порядок — отказ одним списком, ничего не записано.
  Всё остальное считается: секции и хеши — `outline` при том же бюджете (он записан в плане как `weightBudget`: без него сборка получила бы чужие id), решения по узлам — из подтверждённого резолва
  (`resolutions.json`) и правил карты, дайджест раскладки оболочки и корней секций — из канона. План строится только по ПОДТВЕРЖДЁННОМУ резолву (иначе отказ с причинами `resolution_report.check`).
  Запись идемпотентна и побайтно детерминирована (ключи отсортированы, ни времени, ни путей, ни окружения — тест на AST модулей и на двух отдельно собранных репо).
- **План — сверка, а не «файл читается».** `plan.check_frame` пересобирает план из текущих данных (с теми же решениями по раскладке — они лежат в плане) и сравнивает побайтно, затем сверяет `plan.md` с
  отрисовкой `plan.json`. Перетянутое требование, пересобранный канон, правка вердикта/карты/спеки, правка файла руками — `stale` с названной причиной; не JSON / не объект / не UTF-8 / слишком глубокий
  JSON / нет `weightBudget` — `open` («неразбираемый план ≠ pass»); не с чем сверять (канон не читается, хранилище вердиктов пропало) — `unknown`, и он блокирует. Лестница статуса 1.10 читает `plan.json`
  как прежде: JSON-объект (тест на `planned`, на битый файл → `normalized` + `artifact-unreadable`).
- **Порядок сборки.** Три яруса, каждый в порядке документа: секции, СОЗДАЮЩИЕ общие local-компоненты (первое вхождение), затем секции, которые их только используют, затем остальное; occluded не строятся,
  пролог (токены, моки) — не секция и не шаг. Общий local — инстанс с решением `local` и тем же figmaName+variants ≥ 2 раз либо с именем из правила карты (`outcome: local` + `component` — его берёт план, 2.4);
  имя без правила карты — PascalCase латинских слов figmaName, нет латиницы — `Local<N>`, совпадение разных ключей — суффикс 2, 3…
- **Раскладка (§11.4).** Решение по записи: `apply` / `keep-px` (подсказка layoutHints), `keep-px` / `group` (контейнер с абсолютными детьми) и свидетельство `declaration` / `goal-image` / `user` / `none`;
  `apply` и `group` без свидетельства не принимаются (px остаётся px), принятый hint копируется в план из канона; `group` — ряд или колонка из названных детей, `gap` / `gaps` и `box` считает КОД по боксам канона
  (допуск 1 px, порядок — позицией, перекрытие — отказ). Не решённые записи — отказ со списком и подсказкой лестницы; `layoutRest` пишет их как `keep-px` без свидетельства, и они попадают в `planUncertainty`.
- **Контракт.** Шестнадцать id в порядке спеки, у каждого нарушенного пункта `{id, frame?, state, blocking, blockedReason, owner, detail, ask, record?, degradesTo?}` (`record` — чем записать ответ: сверх спеки,
  без него слабой модели не из чего выбрать инструмент). `ready` — нет блокирующих (подпись в них не входит), `complete` — нет и деградаций, `signed`, `blocked` (`plan-incomplete (id…)` / `plan-unsigned`),
  `blocks`, `checks` (16 коротких строк), `planUncertainty` (узел один раз, с диска, переживает нечитаемый план), `toSign` (строки вопроса «Подписываем план?»), `nextStep`. Brownfield-вопросы: адрес и рецепт
  открытия кадра, `devCommand`, `sources` / `scope`, `baseline` — `ask` дословно + `record` через `daiver_track_manifest` (маршрут из таблицы «Кадры» `ui-spec.md` подсказан в вопросе про адрес); полнота
  кадров против таблицы — пункт `requirement` (строка таблицы сопоставляется с кадром по ссылке макета, затем по имени). Упавшая проверка — блокирующий `open` (тест подменяет проверку на исключение).
- **Подпись и lock.** Подпись — не инструмент (`daiver_plan_sign` нет, тест), а согласие `ui-plan-<KEY>` с цитатой, привязанное `record_approval.py --bind-file` к `plan.lock.json`: sha256 требований
  кадров, `plan.json` кадров, `resolution-report.md`, `ui-plan.md`. `signed` — согласие есть, `bound_sha256` равен sha256 lock'а, СОБРАННОГО из текущих артефактов (а не прочитанного: правка plan.json руками
  lock-файл не пересобирает), и файлы на диске ему равны. Писатель (`daiver_plan_contract`), когда контракт готов, пересобирает `ui-plan.md` и lock и снимает устаревшее согласие (`record_approval` не пишет
  второе по активному ключу — как с `ui-resolve`, 2.5); читатель (гейт, `evaluate(write=False)`) ничего не пишет и не снимает (тест: дерево и журнал до и после побайтно равны). Подпись НЕ зависит от `ready`:
  в дайджест не входят блокирующие пункты (файл пишется, только когда их нет), поэтому пропавший на машине браузер — не «план не подписан»; её читает `plan_contract.signature_state` (для `ui-guard`, 3.3).
- **Гейт.** `ui_gate.py design`: 0 только при `ready` + `signed`; иначе 1 и перечень `пункт[кадр]: что не так` (причины резолва 2.5 — среди них), для неподписанного — команда `record_approval`. Тесты 2.5 на гейт
  обновлены: «резолв в порядке» теперь значит «причин резолва в выводе нет», exit остаётся 1, пока нет плана и подписи.
- **Решено там, где спека свободна.** Формат решения по раскладке и `group`; правило общих local-компонентов, их имена и три яруса порядка; смысл `unknown`; определение `planUncertainty`; `resolutions`
  и `signature` блокируют всегда (автономия — 7.1/7.2, D9); `browser` ищет частная функция (4.1 заменит) и называется `no-browser`; поля `sources`/`scope` заведены здесь, не в 6.4, а `baseline` — непустая папка
  `<кадр>/baseline` (захват и запись `baseline: {kind}` — 4.x/6.4); `ui-plan.md` и lock пишет инструмент, не модель; согласие подписи — вопрос `sign-plan` у оркестратора, субагент возвращает
  `needs_input`, а гейт закрывает через `record_gate`; поле `directive` ответа контракта — 7.1.
- **Отклонения** — строки README (пересмотрены: `ui_gate.py design`; новые: plan.json пишет инструмент, порядок сборки и общие local, решения по раскладке, `resolutions` / `signature` блокируют всегда, причины
  останова пунктов, `browser`, `unknown` / `planUncertainty` / `directive`, `baseline` / `sources`, `ui-plan.md`, подпись и lock, `daiver_plan_contract` пишет).
- **Не проверено данными.** Боевых экранов и планов нет: правило общих local-компонентов и их имён; три яруса buildOrder; решения по раскладке и геометрия групп (на «Modal» `unproven` пуст — всё доказано
  синтетикой); как слабая модель читает `open[]`, `ask`, `toSign` и длину ответа; число вопросов контракта и размер `ui-plan.md` на большом экране; пункт `browser` на корпоративной машине GigaCode; пункты
  `sources` / `baseline` — только синтетика (образец страницы — README → «Нужно от пользователя»). Цепочка «ответ `ask_user_question` → `record_approval` → gate-guard» для класса `ui-plan` проверена
  скриптом с цитатой и без, но не хуком на живой сессии; релей вопросов видов `plan-question` / `sign-plan` через `pending_questions` в GigaCode — X.4. Обновить `ui-guard` (3.3): подпись проверять
  `signature_state`, а не хешем файла (заметки в 3.1–3.4, 6.4, 7.1, X.4 добавлены).
