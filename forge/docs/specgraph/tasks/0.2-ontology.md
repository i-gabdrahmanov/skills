# 0.2 — Онтология как данные

**Этап:** 0 · **Зависит от:** 0.1 · **Статус:** todo
**ТЗ:** §2, §3, §8.4, §8.6 · **Решения:** рычаг 3, таблицы «Онтология v1» в 020

## Зачем
ТЗ требует различать виды связей (§8.4) и расширять типы без переделки (§8.6). Если виды узлов и
рёбер зашить в код, каждый новый тип (процесс ARIS, шаг клиентского пути) превращается в правку
валидатора, синка и обхода — так прототип оброс 27 инвариантами. Онтология — один файл, весь код
читает её.

## Что сделать
- `skills/specgraph/references/ontology.json`, версия `1`:
  - `kinds`: для каждого вида — `path` (шаблон: `services/{service}/schedulers/{name}.md`),
    `required` (обязательные скалярные ключи), `key` (формат, если есть), `subkinds`/`roles`
    (для `data`, `kafka-op`), `name` (грамматика: `phrase` | `endpoint` | `topic` | `as_is`),
    `owner` (`service` | `none`), `title_ru` (для легенды и отчётов).
  - `edges`: для каждого прямого ребра — `from[]`, `to[]` (с ограничениями роли:
    `kafka-op(consume)`), `inverse`, `symmetric`, `evidence: required|optional`, `same_service`
    (для `invokes`), `impact: up|down` (в какую сторону идти от изменённого узла к бизнес-
    операциям — нужно `graph_impact`, 3.4), `title_ru`.
  - Содержимое — таблицы «Онтология v1» из 020, без добавлений.
- `sgraph/ontology.py`: загрузка и самопроверка (имена прямых и обратных ключей не пересекаются
  между собой и со скалярными ключами; у каждого вида детерминированный путь; `from/to` ссылаются
  на существующие виды; у симметричного ребра `inverse` совпадает с ним самим). API:
  `edge_allowed(edge, from_node, to_node) -> (ok, reason)`, `inverse_of(edge)`,
  `fm_keys(kind)` (порядок ключей для записи), `path_for(kind, name, service, subkind)`.
- Проверку «примеры ТЗ ложатся в онтологию» сделать таблицей-тестом: каждая связь-пример из ТЗ §3,
  §4.1–4.3, §5, §6, §7 — пара `(from_kind, to_kind)` → ровно одно допустимое прямое ребро.

## Готово, когда
- Самопроверка ловит: дубль обратного ключа, ребро на несуществующий вид, путь без `{name}`
  (тесты на сломанных копиях онтологии).
- Таблица-тест по ТЗ зелёная: у каждого примера ровно одно ребро, неоднозначностей нет.
- В коде вне `ontology.py` нет литералов видов, кроме перечисленных в докстринге модуля (grep-тест).

## Вопросы
- `invokes` → `kafka-op(publish)`: публикация как отдельный узел нужна только тогда, когда спека
  описывает её отдельным разделом (формат сообщения, условия отправки). Иначе ребро
  `publishes_to` идёт напрямую от операции. Правило проговорить в брифе раскладки (1.5).
