# 4.1 — Счётчики прогона и история здоровья графа

**Этап:** 4 (диагностика) · **Зависит от:** 0.1 · **Статус:** done
**Решения:** D18 · **Уроки:** `loop-check.json` прототипа (история 30 прогонов, метка
стабилизации); память: «логи и бюджет удалены из forge» — оверхед хуков-логгеров

## Зачем
Обратная связь из окружения будет только в виде цифр и кодов. Чтобы понять, где ломается
система, движок должен сам считать, что происходило: какие инструменты отказывали модели и почему,
где она переделывала секцию по пять раз, какие правила срабатывали. Логи-хуки forge уже снимал из-за
оверхеда, поэтому считает сам движок в диспетчере инструментов и бесплатно для модели.

## Что сделать
- Обёртка в `sgraph/tools.call`: на каждый вызов — инструмент, исход (`ok` | `rejected` | `error`),
  коды отказа, id секции или заметки (только id), длительность, размер ответа. Запись —
  `.spec-graph/runs/<KEY>/calls.jsonl`, компактно; новые инструменты считаются автоматически.
- Счётчики шага: попытки плана на секцию, брошенные секции (нет плана после N попыток), вопросы
  человеку, решения человека по типам (merge/rename/reject/place), исключения движка.
- `.spec-graph/health.json` — история последних 30 прогонов: узлы по видам, рёбра по типам и
  происхождению (rule/model/manual/improve), `E-*`/`W-*` по кодам, дыры 3.2, покрытие, `unplaced`,
  доля согласия самопроверки (4.5, когда появится). Метка стабилизации: N прогонов подряд без новых
  находок.
- **В счётчиках нет текста исходников:** только id, коды, числа, размеры. Тест-утечка: прогон на
  фикстуре, затем ни одна строка из `sources/` (≥ 4 слов подряд) не встречается в `runs/` и
  `health.json`.

## Готово, когда
- Каждый вызов инструмента на фикстуре оставил запись; исключение внутри инструмента
  записалось как `error` с типом исключения (без сообщения, если в нём может быть текст исходника).
- Тест-утечка зелёный; мутант «записать имя заголовка в счётчик» его валит.
- `health.json` хранит не больше 30 прогонов, метка стабилизации считается.

## Результат
- `sgraph/metrics.py`: `record_call` (по строке на вызов в `.spec-graph/runs/<KEY>/calls.jsonl`), `bump`
  (именованные счётчики шага в `counters.json`), `summarize` (исходы по инструментам, топ кодов отказа,
  единицы с наибольшим числом отказов, ошибки движка), `record_health` (30 снимков, только числа,
  находки — sha1[:12], метка стабилизации — 3 снимка подряд без новых находок), `current_key`
  (свежайший манифест `ground/statements/specgraph/*`, вне прогона — `adhoc`).
- Счёт встроен в `tools.call`: каждый инструмент считается сам, ни одна будущая задача не добавляет
  счёт отдельно. `ToolError` несёт `codes`: отказы проверки аргументов — `E-arg-unknown`,
  `E-arg-missing`, `E-arg-type`, конфиг — `E-config-invalid`. Id единиц работы берутся только из
  аргументов, объявленных в `x-ref-args` схемы (очередь 0.6 объявит `item_id`).
- Защита от утечки — кодом, а не договорённостью: аргументы не пишутся вовсе; от исключения — только
  тип; коды — по формату `E-|W-|I-…` (свободный текст отбрасывается); ref — без пробелов и кавычек, не
  длиннее 200; имена счётчиков и ключи метрик — латиница; находки — хешами.
- Сбой записи счётчика не роняет инструмент (строка в stderr): метрика не важнее работы.
- `.gitignore` проекта (блок install.sh): `.spec-graph/*` вне git, кроме `config.json`, `hints.md`,
  `ontology.local.json`.
- Тесты: `test_run_metrics.py` (9): исходы ok/rejected/error, топ отказов по единицам, формат кодов,
  счётчики, тест-утечка (текст спеки в аргументах, в имени аргумента, в сообщении исключения, в
  метриках и находках здоровья — ни одной последовательности из 4 слов в `runs/` и `health.json`),
  30 снимков, стабилизация, ключ прогона. Мутанты (пишем аргументы, не проверяем коды, текст в
  историю, находки без хеша) пойманы.
- Не сделано здесь (по плану — в других задачах): счётчики вопросов и решений человека появятся
  вместе с инструментами каталога и связей (1.4, 2.6), попытки и брошенные единицы — с очередью
  (0.6), вывод сводки наружу — пакет диагностики (4.3).
