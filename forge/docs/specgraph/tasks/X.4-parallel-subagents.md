# X.4 — Параллельные субагенты: блокировка проекта и пачки

**Этап:** сквозная · **Зависит от:** 0.6, X.2 · **Статус:** done
**Решения:** D14, D23

## Зачем
Субагент на единицу работы — правильно для GLM 5.3 Flash: маленький чистый контекст. Последовательно на
реальной спеке это порядка 2000 вызовов, то есть 15–30 часов. Механика аренды в очереди умела выдавать
несколько единиц, но состояние движка — JSON «прочитать → изменить → записать» без блокировок, и два
одновременных `graph_link_put` теряли бы запись друг друга.

## Что сделать
- Межпроцессная блокировка проекта на время каждого вызова инструмента; модель думает вне блокировки.
- Атомарная запись состояния и заметок vault.
- Пачка единиц для оркестратора: N субагентов одним ходом, без повторной выдачи одной единицы.
- Протокол в SKILL.md; тест на настоящих параллельных процессах.

## Результат
- `sgraph/fsutil.py`:
  - `project_lock(root)` — `.spec-graph/.lock`, `flock` на POSIX и `msvcrt.locking` на Windows; повторно
    входимая в потоке; таймаут 600 с (`SGRAPH_LOCK_TIMEOUT_S`);
  - `write_text` / `write_bytes` — временный файл рядом и `os.replace`.
- `tools.call` выполняет каждый инструмент под блокировкой. Дольше таймаута — отказ `E-busy` («повтори
  вызов»), а не порча состояния.
- Все 37 мест записи движка переведены на атомарную запись (очереди, предложения рёбер, планы, каталог,
  заметки vault, отчёты, счётчики). `queue._save` больше не использует общий временный файл: между процессами
  он сталкивался бы.
- `graph_next batch: true` → `Q.lease_batch`: до `queue.parallel` единиц. Висящие в аренде (их субагент
  оборвался) идут первыми, единица в пачке один раз. Одиночный `graph_next` всегда продолжает висящую:
  последовательный протокол и продолжение после обрыва прежние.
- `queue.parallel` по умолчанию 4. Рантайм не запускает субагентов одновременно — оркестратор исполняет
  пачку по очереди, протокол тот же.
- SKILL.md, «Цикл очереди»: пачка → субагенты одним ходом → дождаться всех → следующая пачка.
- Тесты:
  - `test_concurrency.py` (4): 4 процесса разом сдают пачки link-note, итог байт-в-байт равен
    последовательному прогону, очередь закрыта, журнал вызовов цел, временных файлов нет; блокировка
    межпроцессная (`E-busy` по таймауту, ожидание вместо отказа), повторный вход без самоблокировки;
  - `test_work_queue.py`: пачки — две разные единицы, повтор до сдачи, продолжение висящей, нет дублей.
  Мутанты пойманы: снятая блокировка в диспетчере, пустой `flock`, отключённый повторный вход, дубль
  единицы в пачке.
- **Не проверено:** запускает ли GigaCode субагентов одновременно и делят ли они процесс MCP с сессией.
  Блокировка верна в обоих случаях; ускорение — только если рантайм параллелит. Покажет первый выезд.
