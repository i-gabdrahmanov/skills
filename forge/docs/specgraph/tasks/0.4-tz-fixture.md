# 0.4 — Синтетическая фикстура по ТЗ и эталон графа

**Этап:** 0 · **Зависит от:** 0.2 · **Статус:** done
**ТЗ:** §1 (пример декомпозиции), §4–§7, §10

## Зачем
Реальной спеки в репо нет, и она корпоративная. Все тесты этапов 1–3 и e2e (3.6) опираются на
маленький корпус, повторяющий форму ТЗ, и на эталонный граф, который из него должен получиться.
Эталон — это приёмка ТЗ в машинном виде: переходы §10 записаны путями.

## Что сделать
- `skills/specgraph/fixtures/tz-mini/sources/` — выдуманный, но похожий по форме корпус:
  - `task-service/task-service.md` — общее описание; шедулер формирования задачи
    укомплектования (условия, алгоритм, cron, вызов УПЗ-адаптера, динамические атрибуты); **один**
    шедулер закрытия регулярных задач для укомплектования, регистрации и приёма ТУ; свои шедулеры
    формирования и закрытия задачи передачи упаковок в СЦ-архив; Kafka-обработчик ответа УПЗ;
    публикация в топик; 2 эндпойнта; самостоятельный алгоритм. Внутри — JSON- и SQL-фенсы,
    таблица, длинный раздел, якорная ссылка `](#…)`, картинка `resources/…`.
  - `task-service/task-service-draft.md` — черновая копия (должна исключаться конфигом).
  - `rmoc-service/rmoc-service.md` — эндпойнты, которые использует UI.
  - `upz-adapter/upz-adapter.md` — эндпойнт создания задачи и обработчик топика.
  - `ui/укомплектование.md`, `ui/передача-упаковок.md` — экраны со списком вызовов.
  - `business/*.md` — описания 4 бизнес-операций (для чего / когда / что / результат) и строка
    про связь «укомплектование ↔ передача в СЦ-архив».
- `fixtures/tz-mini/expected/graph.json` — эталон: узлы (`kind`, `name`, `service`, `key`),
  прямые рёбра (`from`, `edge`, `to`, `mechanical: bool`), и `walks` — переходы ТЗ §10 путями:
  - Укомплектование → `closed_by` → Шедулер закрытия регулярных задач → `closes_task` →
    Регистрация, Приём ТУ → `screens` → UI → `calls` → эндпойнт → `belongs_to` → сервис;
  - Передача упаковок → `created_by`/`closed_by` → свои шедулеры (не общие) → … ; `related` →
    Укомплектование;
  - rmoc-service → `operations` → эндпойнт → `called_by` → UI → `ui_of` → операция.
- `fixtures/tz-mini/expected/{drafts,plans,edges}/*.json` — «ответы модели» для e2e
  (заполняются в задачах 1.3, 1.5 и 2.3 по мере появления схем).
- `README.md` фикстуры: что в ней, какой раздел ТЗ покрывает каждый кусок, что выдумано.

## Готово, когда
- Эталон проходит самопроверку онтологии: каждое ребро допустимо `edge_allowed`.
- В эталоне есть ловушки: общий шедулер (один узел, три операции), похожие имена «закрытие
  регулярных» и «закрытие передачи» (два узла), упоминание без взаимодействия (строка «см. также
  rmoc-service» — не ребро), черновая копия (исключена).
- Каждый переход `walks` — цепочка допустимых рёбер эталона (тест).

## Результат
- `fixtures/tz-mini/sources/`: task-service (справочник типов задач, 4 шедулера, обработчик и публикация
  Kafka, 2 эндпойнта, алгоритм с подразделом, 2 набора динамических атрибутов, «См. также»,
  JSON/SQL-фенсы, таблицы, якорная ссылка, картинка), черновик для `exclude`, rmoc-service (3 эндпойнта),
  upz-adapter (эндпойнт с публикацией и внешней УПЗ), 4 экрана, бизнес-описания 4 операций со связью
  передачи и укомплектования. Всё выдумано — README фикстуры.
- `expected/graph.json`: 29 узлов, 45 прямых рёбер (у каждого, кроме `belongs_to`, дословная цитата и
  признак `mechanical`: 31 ребро правило поставит само, 14 — решение модели), 7 переходов ТЗ §10/§4.1.
- `test_tz_fixture.py` (10): узлы и имена по онтологии, владелец = `belongs_to`, каждый исходник кроме
  черновика даёт узлы; рёбра допустимы и подтверждены цитатой из файла; переходы ТЗ проходят по прямым
  и обратным ключам; ловушки (общий шедулер — один узел с тремя операциями, шедулеры передачи свои,
  «См. также» без рёбер, черновик вне графа, пример декомпозиции §1). Мутанты (выдуманная цитата,
  пропавшее ребро общего шедулера, недопустимое ребро, склеенные шедулеры) пойманы.
- Решения там, где задача свободна: экраны Регистрации и Приёма ТУ добавлены (ТЗ §10 переходит «к их
  UI»); публикация события о закрытии — отдельный раздел и узел `kafka-op:publish`, а у upz-adapter
  публикация — фраза внутри эндпойнта: так фикстура проверяет оба способа записи `publishes_to`.
- «Ответы модели» (`expected/drafts|plans|edges/`) появятся с задачами 1.3, 1.5, 2.3.
