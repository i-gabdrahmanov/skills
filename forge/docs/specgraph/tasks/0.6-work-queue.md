# 0.6 — Очередь работ: задачи собирает движок, модель исполняет по одной

**Этап:** 0 · **Зависит от:** 0.1, 4.1 · **Статус:** done
**Решения:** D23 · память: «фазы — субагентом», GLM 5.3 Flash — «дробить мельче»

## Зачем
GLM 5.3 не удержит в голове сотни единиц работы (20 сервисов × 40 секций). На длинной работе она
теряет пункты, путает, что уже сделано, а после обрыва сессии начинает заново. Свой план работ
слабая модель составит так же плохо, и проверить его будет ещё труднее. При этом полный список
единиц известен механически после скана: файлы, секции, заметки, операции. Поэтому список держит
движок, а оркестратор крутит простой цикл без планирования.

## Что сделать
- `sgraph/queue.py`, очередь шага — `.spec-graph/queue/<step>.json`. Единица: `id`, `kind`
  (`draft-file`, `assign-section`, `link-note`, `card`, `selfcheck`, `improve`), ссылки на файл,
  секцию или заметку, имя брифа, `status` (`pending` | `leased` | `done` | `abandoned`), попытки,
  время аренды, исход.
- Очередь строит движок детерминированно из артефактов: блоков, каталога, vault. Модель единиц не
  добавляет; генераторы самопроверки (4.5) и самоулучшения (4.6) — тоже код движка.
- `graph_next(step)` — следующая единица в аренду. В ответе:
  - имя брифа;
  - путь к заранее подготовленному входу `.spec-graph/queue/inputs/<id>.md` (вход маленький,
    вместе с брифом укладывается в бюджет из конфига);
  - инструмент, которым сдать результат;
  - прогресс («12 из 240»).
  Пустая очередь — `пусто`, дальше гейт.
- Инструменты результата (`graph_draft_put`, `graph_assign_put`, `graph_link_put`,
  `graph_card_put`, …) принимают `item_id`. Принятый результат закрывает единицу, отказ добавляет
  попытку. После N попыток (конфиг, по умолчанию 3) единица уходит в `abandoned` с последним кодом
  отказа и попадает в отчёт шага для человека.
- Аренда истекает (субагент оборвался) — единица возвращается в `pending`. После обрыва сессии
  `graph_status` показывает, где остановились, и `graph_next` продолжает с того же места.
- Порядок выдачи детерминирован и задаётся по шагу в конфиге: файлы — в порядке сервисов, секции — в
  порядке документа, заметки — по видам.
- `graph_queue_status(step)` — коротко: счётчики по статусам, топ кодов отказа. Те же цифры
  автоматически уходят в счётчики (4.1) и в раздел 5 диагностики (4.3).
- Кто что вызывает: `graph_next` и `graph_queue_status` — оркестратор (вне `phase_tools`),
  инструменты результата — субагенты шага (`phase_tools`).
- Цикл оркестратора в SKILL.md — пять строк: `graph_next` → субагент с брифом и входом → его отчёт →
  `graph_next` → … → `пусто` → гейт. Параллельность — `queue.parallel` в конфиге, по умолчанию 1.
- Помощник гейта `queue_closed(step)`: всё `done` или `abandoned`; число брошенных — в отчёт.

## Готово, когда
- Одинаковые артефакты → побайтно одинаковая очередь.
- Тесты: аренда и истечение; попытки → `abandoned`; «обрыв» посреди очереди и продолжение без
  повторов и пропусков; результат с чужим или закрытым `item_id` — отказ.
- Вход каждой единицы на «раздутом» варианте 0.5 укладывается в бюджет (крупная секция режется
  на части по границам блоков).

## Результат
- `sgraph/queue.py`: очереди `draft-file`, `assign-section`, `link-note`, `card`, `selfcheck`, `improve` в
  `.spec-graph/queue/<имя>.json`; входы — `.spec-graph/queue/inputs/<id>-<sha8>.md`. `build` (детерминированная
  и бережная пересборка: закрытое с тем же входом остаётся закрытым, изменившийся вход переоткрывает
  единицу и обнуляет попытки, исчезнувшая незакрытая уходит; вход + бриф сверх `budget_chars` — отказ всей
  сборки без записи), `lease`, `check_leased`, `settle`, `status`, `closed`.
- Инструменты оркестратора `graph_next` (единица, бриф, путь ко входу, инструмент результата, прогресс,
  готовая подсказка «что делать дальше»; «пусто» — к гейту) и `graph_queue_status`.
- Контракт результата — в диспетчере, а не в каждом инструменте: схема с `x-queue: <очередь>` и аргументом
  `item_id`. `tools.call` до работы проверяет «единица этой очереди и в аренде» (`E-queue-item`, инструмент
  не запускается), после — закрывает (принято) или списывает попытку (ToolError). Сбой движка попытку не
  списывает: аренда истечёт сама. `item_id` автоматически идёт в ref счётчиков 4.1; брошенная единица
  поднимает счётчик `queue.<имя>.abandoned`.
- Продолжение после обрыва: при `parallel` = 1 повторный `graph_next` до сдачи возвращает ту же единицу
  (`repeat: true`), после истечения аренды — снова её же как новую аренду.
- Настройки — секция `queue` конфига проекта (`parallel`, `max_attempts`, `budget_chars`, `lease_s`; по
  умолчанию 1, 3, 24000 знаков ≈ 6 тыс. токенов, 1800 с), проверяются схемой.
- Бриф `SKILL.md`: раздел «Цикл очереди» — три шага для оркестратора.
- Тесты `test_work_queue.py` (11) с подменёнными часами; мутанты (аренда не проверяется, отказ не
  списывает попытку, параллельность не ограничена, пересборка не бережная) пойманы.
- **Не проверено:** бюджет на «раздутом» варианте стресс-корпуса — корпуса ещё нет (0.5); резка крупной
  секции по границам блоков — дело генераторов очередей (1.3, 1.5), очередь только отказывает на
  превышении.
