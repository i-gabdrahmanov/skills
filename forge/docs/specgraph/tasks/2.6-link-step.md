# 2.6 — Отчёт связей и шаг graph-link

**Этап:** 2 (graph-link) · **Зависит от:** 2.2, 2.5 · **Статус:** done
**ТЗ:** §8.4, §8.5 · **Решения:** D13

## Зачем
Одно решение человека на шаге link — утвердить связи. Аналитику нужно не 300 строк подряд, а
сгруппированный отчёт: что формирует, что закрывает и где UI у каждой операции; какие межсервисные
вызовы найдены; что сомнительно.

## Что сделать
- `_graph/edges-review.md`:
  1. По бизнес-операциям: «Укомплектование: формирует — …; закрывает — …; UI — …; связана с — …».
  2. Межсервисные `calls` / `publishes_to` → `consumes` (кто кому и через что).
  3. `confidence: low|medium` с цитатами.
  4. Отклонённые валидатором с причиной.
  5. Вопросы: неоднозначные цели, призраки, stub-операции.
  6. Узлы, добавленные при раскладке (`catalog.delta.json`, 1.5): принять, слить с существующим,
     переименовать или убрать (блоки уходят владельцу-сервису или в `unplaced`) — через
     `graph_catalog_decide`, после чего повторная нарезка затронутых файлов.
- Инструмент `graph_edges_decide(accept[], reject[])` — вызывает оркестратор после ответа
  пользователя; отклонённое пишется в `_graph/decisions.md` и больше не предлагается.
- Бриф шага в SKILL.md: механические рёбра → цикл очереди `link-note` (0.6) → цикл очереди `card` →
  `graph_sync` → отчёт → решение человека → `graph_sync`.
- `graph_gate.py link`: очереди `link-note` и `card` закрыты; нет предложений в `proposed`; по
  каждому узлу дельты есть решение; неразрешённые оформлены вопросами; синк чистый (повтор — 0
  изменений); согласие
  `graph-edges-<KEY>` привязано к хешу `edges-review.md`.

## Готово, когда
- Тесты гейта: без согласия, с устаревшим отчётом, с висящим `proposed`, с узлом дельты без
  решения — блок.
- Шаг на фикстуре с «ответами модели» проходит до exit 0; отчёт для «Укомплектования» содержит
  оба шедулера и UI.

## Результат
- `sgraph/review.py`, инструменты:
  - `graph_edges_review` — отчёт `_graph/edges-review.md` из шести разделов (операции: формирует / закрывает /
    UI / связана с / процесс / карточка; межсервисные вызовы и топики; сомнительное low/medium с id `r-…` и
    цитатой; отклонённое — брошенные единицы с кодами и отклонённые связи; вопросы; узлы дельты с решением).
    Отчёт детерминирован и не зависит от proposed/accepted. Есть согласие на этот отчёт — висящие proposed
    становятся accepted, отчёт не меняется;
  - `graph_edges_decide(accept, reject, why)` — по id или `{from, edge, to}`; отклонение с причиной идёт в журнал
    `.spec-graph/edge-decisions.json` и `_graph/decisions.md`; механика его не воскрешает;
  - `graph_delta_decide(decisions)` — accept | merge into | rename | drop по узлу дельты. Заметка старого имени
    снимается, нарезка повторяется (drop — блоки в unplaced), предложения перенацеливаются и перепроверяются
    онтологией: после слияния с узлом другого вида связь становится rejected с причиной.
- `_graph/decisions.md` общий: каталог, узлы дельты, отклонённые связи (`catalog.write_decisions_md`).
- `sync(dry=True)` — сухой прогон без записи; по нему гейт проверяет «синк чистый».
- `graph_gate.py link`: очереди link-note и card построены и закрыты; узлы дельты решены; синк чистый; отчёт
  свежий; согласие `graph-edges-<KEY>` привязано к хешу отчёта; висящих proposed нет.
- SKILL.md: раздел «Шаг graph-link»; статус — готовы map и link, check — exit 3.
- **Найден и исправлен баг forge:** `record_approval.py` молча пропускал повторное «да» по ключу с активным,
  но устаревшим согласием (привязанный файл изменился). Шаг после правок не закрывался никогда; каталог
  (1.4) был задет так же. Теперь согласие на другое содержимое (`--bind-file` с новым хешем) записывается,
  повтор на то же содержимое пропускается, как раньше. Тест в `test_record_approval.py`.
- Фикстура: шаг проходит до exit 0; в отчёте у «Укомплектования» оба шедулера, UI и связанная операция.
- Тесты `test_link_step.py` (15). Мутанты пойманы: проверки гейта, принятие после согласия, журнал отклонённого,
  снятие заметки, перенацеливание и перепроверка, unplaced при drop, сухой синк, обязательная причина,
  rebind в record_approval.
- **Отклонения:** узлы дельты решаются отдельным `graph_delta_decide`, а не `graph_catalog_decide`: решение не
  меняет утверждённый снимок каталога и не снимает согласие на него. Вопросы пока в отчёте связей, а не в
  отдельном `_graph/open-questions.md` (это 3.2). **Не проверено:** дельта на живой спеке — в фикстуре её нет,
  в тестах она подложена.
