# 3.4 — MCP обхода графа агентом

**Этап:** 3 (graph-check) · **Зависит от:** 3.1 · **Статус:** done
**ТЗ:** §8.2, §10 · **Решения:** D7, D14 · **Уроки:** режим B прототипа (типовые обходы),
бенч 2026-10-27 (стоимость ответа определяется числом раундов модели, а не скоростью поиска)

## Зачем
Второй читатель графа — агент. Если он читает YAML заметок файлами, слабая модель тратит много
раундов и путается в направлениях рёбер. Инструменты отвечают на типовые вопросы за один вызов
и коротко, а `[[ссылки]]` в ответе ведут человека в Obsidian.

## Что сделать
- Индекс из FM vault, кэш `.spec-graph/index.json` с инвалидацией по mtime и размеру; 1000
  заметок индексируются быстрее 1 с на 3.9.
- Инструменты (выдача — строки `[[имя]] (kind, svc) —ребро→ [[имя]]`, жёсткие потолки):
  - `graph_find(q, kind?, limit≤20)` — по имени, алиасу, `key`;
  - `graph_node(name, body: none|card|source|evidence, max_chars)` — рёбра, сгруппированные по
    типам, и выбранная часть тела;
  - `graph_neighbors(name, edges?, dir: out|in|both, depth≤3, limit)`;
  - `graph_path(from, to, max_depth≤6)` — кратчайшие типизированные пути с направлением шагов;
  - `graph_impact(name)` — вверх до бизнес-операций, экранов и процессов: что затронет изменение
    эндпойнта, топика, данных или шедулера. Направление «вверх» задаётся онтологией (поле `impact`
    у рёбер), а не кодом;
  - `graph_service_links(svc)` — производный вид «сервис ↔ сервис» с операциями-посредниками (D7).
- Раздел «Режим вопросов» в SKILL.md: какой инструмент для какого вопроса (найти; кто вызывает;
  что затронет; как связаны A и B; путь операции от UI до сервисов). Grep — только для поиска по
  прозе, когда нет ни имени, ни ключа.
- Инструменты читающие — вне `phase_tools`, доступны на любом шаге и вне конвейера.

## Готово, когда
- Каждый `walk` эталона фикстуры проходит через инструменты: цепочка в ответе совпадает с
  эталоном.
- Потолки соблюдаются (тест на большом синтетическом vault); `EXPECTED_TOOLS` дополнен.
- `graph_impact` от шедулера закрытия регулярных задач возвращает три операции и их экраны.

## Результат
- `sgraph/traverse.py`, инструменты:
  - `graph_find` — по имени, алиасу или ключу; сначала точное совпадение, затем префикс, затем подстрока; ≤ 20;
  - `graph_node` — рёбра по ключам, прямые и обратные, с подписью из онтологии; `body`: card / source /
    evidence; `max_chars` ≤ 4000, обрезка с пометкой;
  - `graph_neighbors` — `edges` (имена рёбер или обратных ключей), `dir`, `depth` ≤ 3, `limit` ≤ 50;
  - `graph_path` — до 3 кратчайших путей, `max_depth` ≤ 6;
  - `graph_impact` — по полю `impact` рёбер;
  - `graph_service_links` — вызовы и топики между сервисами, со стороной издателя и читателя.
  Выдача — строки `[[a]] (вид, сервис) —ребро→ [[b]]`; потолки срезают с флагом `clipped`. Неизвестное имя
  даёт отказ `E-node-unknown` с похожими именами. Все шесть — читающие, вне `phase_tools`.
- Индекс строится из frontmatter vault: узлы и прямые рёбра, симметричное ребро — в обе стороны, даже если
  ссылка есть только с одной стороны. Кэш `.spec-graph/index.json` по подписи «путь, mtime, размер» и
  версии онтологии.
- Шаг пути подписан ключом свойства: прямое ребро — его имя, шаг против ребра — обратный ключ. Так путь
  совпадает с записью `walks` эталона.
- Принадлежность сервису (рёбра `evidence: optional`) в пути допустима только первым шагом из сервиса или
  последним в сервис, иначе путь срезает через узел сервиса (D7).
- Онтология: новое значение `impact: both`, оно у `ui_of`. Экран и его задача затрагивают друг друга,
  поэтому `graph_impact` от шедулера доходит до операций и их экранов без кода под виды.
- SKILL.md: раздел «Режим вопросов» — таблица «вопрос → инструмент».
- Фикстура:
  - все 7 переходов ТЗ §10 проходят по шагам через `graph_neighbors`;
  - для 6 из них `graph_path` возвращает цепочку эталона ровно. Седьмой («укомплектование → … → сервис»)
    — повествовательный, длиннее кратчайшего пути;
  - `graph_impact` от общего шедулера закрытия даёт ровно три операции и их экраны.
- Синтетический vault в 1001 заметку: индекс без кэша — около 0,05 с на 3.9; потолки соблюдаются.
- Тесты `test_traversal.py` (15); 20 мутантов пойманы.
