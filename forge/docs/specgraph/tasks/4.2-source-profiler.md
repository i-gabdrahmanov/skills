# 4.2 — Профайлер входа без содержимого

**Этап:** 4 (диагностика) · **Зависит от:** 1.1 · **Статус:** done
**Решения:** D17, D22

## Зачем
Мы не увидим реальную спеку, но можем увидеть её форму: глубину заголовков, стиль нумерации,
какие слова-маркеры встречаются, как записан API, сколько фенсов и каких языков. По форме видно,
почему правило промахнулось, и можно воспроизвести случай синтетикой (0.5). Тот же профайлер
описывает незнакомые XML и CSV — на нём строятся адаптеры ARIS и клиентских путей (6.2, 6.3).

## Что сделать
- Инструмент `graph_profile(scope)`, для Markdown по файлу:
  - размер, строки, кодировка, BOM, CRLF; блоки по типам; гистограмма глубины заголовков;
  - «формы» заголовков: шаблон нумерации (`N.N.N`, `N)`, «Раздел N»), жирное вместо заголовка, коды
    в скобках, длина в словах;
  - словарь слов заголовков: слова из общего словаря (`references/generic-words.txt`: шедулер,
    алгоритм, обработка, запрос, ответ, топик, задача, атрибуты, экран, сервис, endpoint, consumer,
    job… — без доменных) показываются как есть, остальные — хешем `w#3fa2` с частотой;
  - формы таблиц (число колонок, общие слова шапок), языки фенсов, типы ссылок, число попаданий
    `METHOD /path`, шаблона топика, cron.
- Для XML: пути элементов с частотами, имена атрибутов, тип значений (id-подобное / число / дата /
  текст длины N) — без значений. Для CSV/XLSX: колонки и типы значений.
- `graph_profile --reveal w#3fa2` — только локально, в окружении: показать, какое слово стоит за
  хешем (чтобы пользователь мог по запросу сказать «это слово значит шедулер»). В диагностику
  раскрытые слова не попадают.
- Соль хеша — на проект (`.spec-graph/salt`): одинаковое слово в разных прогонах даёт одинаковый
  хеш, поэтому динамику видно между диагностиками.

## Готово, когда
- Профиль фикстуры и всех вариантов 0.5 не содержит ни одного недопустимого слова (тест-утечка, как
  в 4.1).
- По профилю «английского» и «жирного» вариантов 0.5 их отличие от базового видно глазами.
- Профиль XML на синтетическом BPMN-файле показывает структуру элементов без значений.

## Результат
- `sgraph/profile.py`: `profile` / `profile_md` — по файлу размер, строки, CRLF, BOM, блоки по видам,
  уровни заголовков, формы заголовков (`N`, `N.N`, `N.`, `razdel`, `code`, `http`, `none`, плюс
  `bold_line` и `setext`), слова заголовков (топ 30), формы таблиц и слова шапок, языки фенсов, типы
  ссылок, попадания `METHOD /path`, шаблона топика и cron, предупреждения блоков; `totals` по проекту.
  `profile_xml` — пути элементов (последние 3 уровня), имена атрибутов, ТИПЫ значений (`id`, `number`,
  `date`, `bool`, `text<20|<200|200+`, `empty`); `profile_csv` — колонки и типы. `reveal` — раскрыть
  `w#…`/`f#…` локально. `leaked_words` — проверка утечки по структуре JSON (ключи и перечислимые
  значения схемы разрешены, хеши вычищаются).
- `references/generic-words.txt` — общий словарь (виды операций, структурные слова, служебные термины,
  методы HTTP, форматы); всё вне него — солёным хешем. Соль `.spec-graph/salt` — на проект, вне git.
- Инструмент `graph_profile(scope, reveal)`.
- Тесты `test_source_profiler.py` (5): утечка на фикстуре и всех 16 вариантах (ни одного слова вне
  словаря, ни 4 слов подряд, пути хешами), соль стабильна в проекте и разная между проектами, reveal,
  различимость вариантов (английские заголовки, жирные строки, setext, CRLF/BOM, незакрытый фенс,
  HTML-таблицы, языки фенсов, якорные ссылки), XML и CSV без значений. Мутанты (слова без хеша, общая
  соль, путь в открытую, значения XML) пойманы.
- **Решение:** имена тегов и атрибутов XML показываются как есть — это словарь формата, без него по
  профилю не построить привязку (6.2); значения не показываются никогда. Не-ASCII имя тега — хешем.
- **Не проверено данными:** полнота общего словаря — что окажется доменно-нейтральным в реальной спеке,
  покажет первая диагностика (доля хешей в `heading_words`); словарь пополняется по разбору 4.4.
