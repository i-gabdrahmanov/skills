# 4.4 — Разбор обратной связи: директива и инструмент

**Этап:** 4 (диагностика) · **Зависит от:** 4.3 · **Статус:** done
**Образец:** `BATTLE-TEST-DIRECTIVE.md` (шкала серьёзности, «правдоподобие»), бэклоги `tasks/016`,
`tasks/017`; память: «вставка про прогон forge — это баг-репорт»

## Зачем
Пользователь принесёт из окружения пакет диагностики (или вставку из терминала) и словами расскажет,
что видел. Разбор должен идти по одной процедуре: с чем пришли → класс проблемы → правка → регресс-
фикстура той же формы → новая версия. Иначе каждое исправление чинит случай, а не класс, и следующий
выезд приносит его же.

## Что сделать
- `docs/specgraph/FEEDBACK-DIRECTIVE.md` — процедура для разработчика (и агента-исполнителя):
  1. Версия из пакета → какой тег был в окружении; известное по прошлым выездам — сменой статуса,
     а не новой находкой.
  2. Класс находки: **правило** (экстрактор не видит форму), **бриф** (модель путает, видно по
     кодам отказа и попыткам), **онтология** (нет вида или ребра — кандидаты 4.9), **баг** (`error`,
     неверный код), **окружение** (установка, рантайм, MCP), **данные** (спека противоречива — не
     наше, в open-questions).
  3. Серьёзность: **P0** — граф врёт (ребро без основания прошло, текст потерян, утечка в пакете);
     **P1** — шаг не проходит без рецепта выхода; **P2** — низкое качество (много `unplaced`,
     промахи правил, много вопросов человеку); **P3** — косметика.
  4. На каждую правку — регресс: трансформация или синтетический блок той же формы в стресс-корпус
     (0.5), по профилю из пакета. Без регресса правка не закрыта.
  5. Выпуск: тег (`forge/` линия spec-graph, правила тегов forge), в теле тега — «что поправлено
     по diag-<дата>».
  6. Журнал выездов `docs/specgraph/field/<дата>.md`: что пришло, классы, что сделано, что
     осталось и чему не верить.
- `skills/specgraph/scripts/tools/diag_triage.py <diag.md>` — разбирает машинный блок пакета и
  печатает таблицу-черновик: находки по классам с порогами (доля промахов правила > X, коды отказа
  > Y на секцию, падение доли согласия самопроверки и т. п.), сравнение с прошлым пакетом той же
  соли (динамика).
- Шаблон вопросов пользователю, когда пакета мало: что делали, на каком шаге, что ожидали, что
  увидели в Obsidian — короткий список, без запроса данных спеки.

## Готово, когда
- Директива написана; `diag_triage.py` на пакетах фикстуры и сломанных мутантов выдаёт ожидаемые
  классы (тест).
- Пробный цикл на синтетике: мутант правила → пакет → разбор → правка → регресс в 0.5 → пакет
  чистый. Записан как пример в журнале выездов.

## Результат
- `docs/specgraph/FEEDBACK-DIRECTIVE.md` — процедура: с чем пришли → версия → класс (правило, бриф,
  онтология, баг, окружение, данные; признаки в пакете и куда правка) → серьёзность P0–P3 → регресс
  (вариант той же формы сначала, правка потом) → выпуск → журнал выездов; шаблон вопросов пользователю без
  запроса данных спеки.
- `scripts/tools/diag_triage.py <diag.md> [--prev] [--json]` — черновик разбора по машинному блоку пакета:
  находки по классам с порогами (доля ложных срабатываний > 0,3 при ≥ 3, код отказа ≥ 5 на прогон, доля
  неразмещённого > 10 %), сортировка по серьёзности, динамика против прошлого пакета, вопросы пользователю,
  если прогонов нет.
- Пробный цикл на синтетике — `docs/specgraph/field/2026-11-06-trial.md`:
  - новый вариант стресс-корпуса `sched-reglament` («Регламентное задание» вместо «Шедулер»);
  - пакет до правки → находка «правило, R-scheduler-heading, промахов 4, h3:N.N»;
  - правка маркеров (`регламентн`, `cron`, `крон`, `фонов`) → вариант проходит все столбцы матрицы,
    находки нет, динамика «4 → 0».
  Это реальное улучшение правил, а не только демонстрация.
- Тесты `test_diag_triage.py` (6): фикстура — только «данные P3»; классы бага, брифа и окружения; порядок по
  серьёзности; CLI; сломанное правило; пробный цикл целиком. 11 мутантов пойманы.
