# Задача 014 — Инвертированная полярность RED-судьи и слепые причины отказа

## Статус
Закрыта · исправлено 2026-08-28

## Контекст
Найдено на первом прогоне full-ветки против НАСТОЯЩЕЙ сборки (метапроект `metagradle`:
Gradle 8.14 + Spring Boot 3.3.0 + JaCoCo). Ни статическим чтением, ни юнит-тестами эти
дефекты не видны: они проявляются только когда судья реально запускает gradle.

### 14.1 `red-judge` засчитывал ЗЕЛЁНЫЕ тесты как валидный RED
`run_judge.check_red` — судья фазы, смысл которой «тест обязан падать на ещё не
реализованном поведении», — оценивал прогон так:

```python
passed = r.returncode == 0        # ← gradle вернул 0 == тесты ЗЕЛЁНЫЕ
```

То есть:
- корректное RED-состояние (компилируется, тесты фичи падают) → **FAIL**, шаг `04-test-*`
  закрыть нельзя;
- состояние «RED не написан, всё зелено» → **PASS**.

Судья поощрял ровно то, что фаза запрещает. На одном и том же состоянии проекта
детерминированный гейт и судья давали противоположные вердикты:

```
check_tests_red: pass — компиляция OK; 2/2 выполненных тестов красные — корректное RED
red-judge:       FAIL — RED-judge root: tests FAILED (> Task :test FAILED)
```

Почему не ловилось: в юнит-тестах судья до gradle не доходил — без `feat_classes` (тест-классы
фичи из `tasks[].artifacts`) срабатывал fail-open по scope, и ветка с `returncode` не
исполнялась ни разу.

### 14.2 Причина отказа чекера не доезжала до модели
`run_judge` брал `(stderr or stdout)[:200]`. Детерминированные чекеры печатают JSON-отчёт,
начинающийся с абсолютного пути, — и 200 символов уходили целиком на путь:

```
check_sdd_doc FAIL: {\n  "status": "fail",\n  "sdd": "/private/tmp/.../ORD-101/
```

Реальных причин было восемь («нет обязательный раздел SDD: «модель угроз»», «не найден ни один
сценарий Given-When-Then»), до `errors.json` не доехала ни одна. А именно `errors.json`
скармливается субагенту на ре-итерации — цикл исправления кормили пустышкой.

### 14.3 Вторая копия устаревшего рецепта согласия
`run_judge` печатал тот же рукописный маркер `ground/approvals/gate-override-<judge>.json`,
что и `update.py` до задачи 013 (13.2). Путь заблокирован `state-write-guard` и не
засчитывается без провенанса `record_approval`.

### 14.4 Детектор Given-When-Then требовал одну строку
`check_sdd_doc._has_gwt` искал `given.*when.*then` построчно. Канонический Gherkin пишут в три
строки — и такой SDD отклонялся с сообщением, из которого требуемая форма не следует. На
прогоне корректная спека была отклонена трижды подряд и сожгла лимит ре-итераций до ESCALATE.

## Критерии приёмки
- [x] `check_red`: падающие тесты фичи — валидный RED; `exit 0` — блокирующий отказ «тесты
      ЗЕЛЁНЫЕ, это не RED»; ошибка компиляции — отдельный отказ «RED обязан компилироваться».
- [x] Проверено на настоящей сборке в обе стороны: стаб + падающие тесты → PASS; реализация
      (тесты зелёные) → FAIL с внятной причиной.
- [x] `_fail_detail`: из JSON-отчёта чекера вытаскиваются `errors`/`warnings`, лимит 800;
      сырой вывод — прежним способом.
- [x] Рецепт согласия в `run_judge` указывает на `record_approval.py`.
- [x] `_has_gwt` понимает многострочный сценарий (markdown-жирный, списки, цитаты) в окне
      12 строк; заголовок «(Given-When-Then)» и разнесённые по документу слова — не сценарий.
- [x] Регрессионные тесты на полярность (три случая: red / green / compile-fail).

## 14.5 Гейт покрытия молча проходил на любом одномодульном проекте

Найдено на том же прогоне, при первой попытке посчитать покрытие по реальной дельте фичи.

`check_coverage._changed_java` фильтровал изменённые файлы условием `"/src/main/" in f`.
`git diff --name-only` отдаёт пути **от корня репозитория**: в одномодульном проекте это
`src/main/java/...` — без ведущего слэша. Совпадения нет, все файлы отбрасываются,
`changed: 0` — а при пустом списке гейт возвращает `status: pass`.

```
до фикса:  {"status": "pass", "changed": 0, "files": []}
после:     {"status": "fail", "changed": 2,
            "files": [{"path": ".../OrderController.java", "coverage": 0.0, "status": "LOW"},
                      {"path": ".../OrderService.java",    "coverage": 1.0, "status": "OK"}]}
```

То есть гейт, ради которого существует фаза `05-tests`, на одномодульном репозитории
проходил ВСЕГДА, независимо от реального покрытия. В многомодульной раскладке
(`service/api/src/main/...`) подстрока совпадала, поэтому дефект и дожил до e2e.

Ровно этот класс уже чинили в `eval-guard._is_src_main` («требование ведущего слэша молча
fail-open'ило EDD-гейт»), но в `check_coverage` он остался.

- [x] Фильтр переведён на `(?:^|/)src/main/` и `(?:^|/)src/test/|(?:^|/)test/`.
- [x] Проверено на настоящем JaCoCo-отчёте: до фикса `pass` при 0% на новом контроллере,
      после — `fail` с указанием файла и покрытия.
- [x] Регрессия на обе раскладки в `test_check_coverage.py`.

## 14.6 `red-judge` выдавал PASS, не запустив ни одного теста

Из того же прогона: когда судья не мог определить тест-классы фичи, он писал WARN
(`test:scope`) и возвращал `passed=True` со сводкой **«0/1 modules passed»**. То есть фаза RED
закрывалась вердиктом судьи, который не выполнил ни одной проверки.

Осторожность в исходном решении была оправдана — гнать ВСЕ тесты модуля нельзя, чужой упавший
тест заблокировал бы фичу. Неверен был вывод: «не могу проверить» — это не «всё хорошо».
До этой ветки доходят только фичи с задачами, которые пишут код и не test-exempt (иначе выше
срабатывает early-return `test:exempt`), поэтому пустой scope — дефект плана, а не легальный
случай.

- [x] Пустой scope — блокирующий отказ с рецептом («впиши тест-файлы задачи в
      `tasks[].artifacts` рядом с прод-файлами»), а не WARN+PASS.
- [x] Проверено на живом проекте в обе стороны: корректный план → судья работает как прежде;
      тест-файл убран из `artifacts` → блок с внятной причиной.
- [x] Регрессия в `test_run_judge_guards.py`.
