# Задача 004 — Рассмотреть инициализацию git-репозитория в forgeExt

## Статус
Открыта · не исправлять · это наблюдение, а не дефект

> Проверено 2026-08-28: связана с 001, чей тест сейчас проходит и без git-предков.

## Контекст
Каталог `forgeExt` (source-репо extension'а) **не инициализирован как git-репозиторий**
(нет `.git` ни в `forgeExt`, ни в предках `~/Documents`, `~/Users`, `/`) и не является
Java-проектом (нет `build.gradle`/`pom.xml`).

## Почему это важно
Часть механизмов харнеса опирается на git/build-маркеры корня проекта и не сможет работать
внутри самого extension-репо:
- `find_project_root()` (функция `hooks/_project.py`) в extension-репо отдаёт сам `forgeExt`
  как fallback (это ломает тест задачи 001);
- `git_toplevel()` — корень репозитория;
- rollback-чекпойнты и журнал файлов (`file-journal`, `rollback.py`);
- `check_architecture.py` через `git diff`;
- baseline `module_tests.py snapshot`.

Для **работы харнеса** это, скорее всего, **ожидаемо**: extension ставится в целевой
Java-проект и все эти механизмы работают там. Но для **самотестирования харнеса в
source-репо** отсутствие git/build-маркеров создаёт ложно-красные проверки (в т.ч. задача 001).

## Следствие
- CI-проверки харнеса в source-репо недетерминированы по окружению.
- Необходимо решить: инициализировать ли git в `forgeExt` (даст корень для
  `find_project_root`/`git_toplevel`), либо переопределить инварианты тестов, чтобы они
  распознавали корень extension'а по `hooks/`+`skills/`, а не по `.git`/build-файлам.

## Критерии приёмки (необязательные, при принятии решения)
- [ ] Зафиксировано решение: инициализировать git в source-репо ИЛИ адаптировать резолвер/тесты.
- [ ] Если git инициализируется — убедиться, что `.gitignore` покрывает `ground/`,
      `__pycache__/` и локальный `config.json` (уже присутствует).
- [ ] Если решено не инициализировать — закрыть задачу 001 через адаптацию теста.
