# spec-graph — граф спецификации

Конвейер из трёх шагов, на каждом — одно решение человека. Весь детерминированный труд делает
движок (MCP `spec-graph`, инструменты `graph_*`); модель решает только то, что требует понимания
текста, и только по одной единице работы за раз.

| шаг | что делает | решение человека | гейт |
|---|---|---|---|
| `graph-map` | разведка спеки, каталог узлов, нарезка в vault | утвердить каталог и scope (до нарезки) | `graph_gate.py map` |
| `graph-link` | связи с цитатами-основаниями, карточки бизнес-операций | утвердить отчёт связей | `graph_gate.py link` |
| `graph-check` | валидатор, полнота, Obsidian-слой, смоук обхода | принять граф | `graph_gate.py check` |

## Первый ход

1. `graph_status`.
2. Не инициализирован — задай пользователю вопросы из ответа (`questions`): кандидатов предлагай
   первыми, с их доказательствами, решает пользователь. Пути не угадывай.
3. `graph_init` с ответами. Конфиг (`.spec-graph/config.json`) уже есть — `graph_init` его не
   перезапишет; ошибки конфига (`errors`) покажи пользователю.
4. **Прогон.** `graph_status` после инициализации отдаёт блок `run`: ключ прогона (`GRAPH-<N>`),
   текущий шаг и ГОТОВЫЕ команды. Прогона нет — выполни `run.commands.init` в shell как есть и снова
   `graph_status`. Без прогона шаги никуда не записываются, а согласия не привязываются к графу.

**Граф заново** («заархивируй граф», «строим новый») — `graph_archive` с просьбой пользователя в `reason`:
движок уносит своё состояние и vault в `.spec-graph/archive/<метка>/`, конфиг остаётся. Руками vault не
переноси — журнал решений и очереди старого графа останутся и перейдут в новый. Живой прогон — отказ с
командой, как его бросить (только после явного «да» пользователя).

**Закрытие шага** — всегда одной парой команд из `graph_status` (`run.commands`): `gate` (гейт шага
через record_gate), затем `close` (update.py). Гейт не прошёл — причины в выводе; исправляй названное.
Команды не переписывай и не сокращай: путь и ключ в них уже верные.

## Шаг graph-map — разведка, каталог, нарезка

Порядок для оркестратора (ты — оркестратор; единицы работы исполняют субагенты):

1. `graph_survey` — механический обзор и очередь `draft-file`; scope из аргумента `/forge-graph` (имя сервиса,
   каталог или файл; пусто или `all` — всё) передай в его `scope`. Покажи пользователю коротко объём работ
   и аномалии из ответа.
2. Цикл очереди `draft-file` (ниже): субагент по брифу `draft-file.md` сдаёт `graph_draft_put`.
3. `graph_catalog` — каталог узлов. Узлы правил (ключи http/kafka/task/table, операции по папкам
   `[код] Имя` и реестру кодов, таблицы из SQL) движок ставит сам — модель их не подтверждает. Покажи
   пользователю объём, scope и пункты `to_decide` из ответа: первыми — `drift` (вид просел к прошлому
   каталогу: это решение или регрессия?) и `missing_codes` (коды типов задач из спеки без узла), затем
   одинаковые имена, противоречия, пары «это один узел?»; полный список узлов — в `_graph/catalog.md`,
   его открывает пользователь (Obsidian), сам целиком не читай — только нужное место поиском.
   Спроси: утвердить каталог и scope или что поменять.
   Одинаковые имена у разных узлов (`collisions` > 0) — сначала решение: rename по id (имена
   предложены в отчёте) или merge, если это один узел; с коллизиями каталог не утверждается.
   Непринятые решения журнала (`decision_problems`) — показать и переписать или снять (revoke).
   - Правки пользователя — `graph_catalog_decide` (поле `action`: merge/split/rename/move/drop/scope,
     retype — сменить вид узла (`kind`, `role`/`subkind`), revoke — снять запись журнала; у каждой, кроме revoke,
     `why` со слов пользователя; лишнее поле — отказ), затем снова `graph_catalog` и снова вопрос. Узел в
     решении — id `n-…` или имя, которое носит ровно один узел; на одноимённые инструмент откажет и
     перечислит id. `decision_problems` в ответе `graph_catalog` — решения, применённые не так, как
     записаны: покажи их пользователю.
   - «Да» — запиши согласие командой из поля `next` ответа `graph_catalog` (`record_approval.py … --bind-file
     .spec-graph/catalog.json --evidence "<ответ дословно>"`), затем `graph_catalog` — снимок утверждённого
     каталога. Без «да» пользователя согласие не пиши.
4. `graph_assign_start` — очередь `assign-section` (без согласия — отказ).
5. Цикл очереди `assign-section`: субагент по брифу `assign-section.md` сдаёт `graph_assign_put`.
6. `graph_split` — заметки vault; в ответе — полнота и дословность.
7. Гейт: `graph_status` → `run.commands.gate`, затем `run.commands.close`. Не прошёл — причины в выводе; исправляй
   названное (обычно: открытая очередь, устаревшее согласие, блоки без назначения).

`graph_draft_put` и `graph_assign_put` — инструменты субагента единицы; главный агент их не вызывает.

## Шаг graph-link — связи, карточки, отчёт

1. `graph_edges_mechanical` — рёбра по правилам (HTTP, топики, данные); модель их не повторяет.
2. `graph_link_start`, затем цикл очереди `link-note`: субагент по брифу `link-note.md` сдаёт
   `graph_link_put` — связи заметки с дословной цитатой-основанием.
3. `graph_card_start`, затем цикл очереди `card`: субагент по брифу `operation-card.md` сдаёт
   `graph_card_put` — карточку бизнес-операции со ссылками на блоки.
4. `graph_sync` — связи во frontmatter заметок, обратные ключи, таблицы оснований.
5. `graph_edges_review` — отчёт `_graph/edges-review.md`. Покажи его пользователю: операции (кто
   формирует, кто закрывает, UI), межсервисные связи, сомнительное, отклонённое, вопросы, узлы раздела 6,
   прочие связи (раздел 7: их «да» тоже утверждает).
   Спроси: утвердить связи или что поменять. Узлы раздела 6 без решения (`delta_undecided` > 0) —
   сначала они: спроси по каждому и прими решения, согласие на связи — только после (иначе оно устареет).
   - Цели без узла (раздел 5, по числу ссылок) — спроси, для каких создать заглушки (узел без текста
     спеки: таблица, внешняя система); его выбор — `graph_stubs_decide` (`targets`, `why` с его слов), вопросы
     к этим целям сами станут связями.
   - Отклонить связь — `graph_edges_decide` (`reject`: id `r-…` из отчёта или `{from, edge, to}`, `why` —
     со слов пользователя). Узел раздела 6 — `graph_delta_decide` (accept | merge `into` | rename `name` |
     drop, у каждого `why`); после него — шаги из поля `next` ответа (затронутые единицы очередей).
   - После правок — `graph_sync`, снова `graph_edges_review` и снова вопрос.
   - «Да» — запиши согласие командой из поля `next` ответа (`record_approval.py … --bind-file
     <vault>/_graph/edges-review.md --evidence "<ответ дословно>"`), затем снова `graph_edges_review` —
     он примет оставшиеся связи. Без «да» пользователя согласие не пиши.
6. Гейт: `graph_status` → `run.commands.gate`, затем `run.commands.close`.

`graph_link_put` и `graph_card_put` — инструменты субагента единицы; решения (`graph_edges_decide`,
`graph_delta_decide`) — только со слов пользователя.

## Цикл очереди (как исполняется работа модели)

Список работ шага строит движок; ты его не составляешь и не решаешь, что делать дальше. Субагенты
работают **параллельно, пачками**:

1. `graph_next` с именем очереди и `batch: true` — пачка до `queue.parallel` единиц (по умолчанию 4).
2. Ответ «единицы» — запусти по субагенту на КАЖДУЮ единицу пачки. Промпт субагента — поле `prompt`
   ответа как есть, с `{item_id}` и `{input}` его единицы; своего не дописывай (каждое лишнее слово
   остаётся в твоём контексте на весь шаг — так набегал 413). Субагент сдаёт `tool` со своим `item_id` и
   отвечает одной строкой `{"step_id": "<шаг>", "status": "unit"}` (так forge видит, что шаг шёл через
   субагентов). Сам единицы не исполняй и одну единицу двум субагентам не давай.
3. Дождись, пока сдадут все субагенты пачки, затем снова `graph_next batch` с `after` = `cursor` из
   прошлого ответа (без него рантайм принимает цикл очереди за зацикливание и рвёт ход). Ответ «пусто» —
   очередь закрыта, переходи к гейту шага.

Одновременные сдачи безопасны: движок выполняет вызовы `graph_*` по одному под блокировкой проекта, а
думают субагенты параллельно. Отказ `E-busy` — проект занят дольше таймаута: повтори вызов. Если рантайм
запускает субагентов только по одному — исполняй пачку по очереди, протокол тот же.

Отказ инструмента результата оставляет единицу за тем же субагентом (попытка + 1): он исправляет
названное в ошибке и сдаёт снова тем же `item_id`. После трёх отказов единица брошена и попадёт в отчёт
человеку — не обходи это: блоки брошенной единицы раскладки уходят в `_graph/unplaced.md`. Вернуть брошенные
единицы в работу — `graph_queue_retry` (`queue`, `why`), только если пользователь сам это решил. Вход единицы всегда в бюджете; `oversize` в ответе сборки очереди — неделимые
куски (один блок) сверх бюджета, они идут как есть, конфиг не трогай. Оборвалась сессия — начни цикл заново: пачка вернёт
недоделанные единицы первыми. Сводка — `graph_queue_status`.

## Шаг graph-check — проверка и приёмка

1. `graph_check` — валидатор (ошибки, дыры полноты, перенос исходников), Obsidian-слой, смоук обхода.
2. Есть ошибки (`errors`) или проблемы обхода (`smoke`) — покажи пользователю первые (`top`) и `_graph/report.md`.
   Исправляют их шаги конвейера (повторить map или link), не правка заметок руками.
3. Ошибок нет — покажи сводку: счётчики, дыры по бизнес-операциям (`_graph/open-questions.md` — вопросы
   аналитику), раздел «Перенос исходников» (какой файл перенесён полностью). Спроси, принимает ли он граф.
   - «Да» — запиши согласие командой из поля `next` (`record_approval.py … --bind-file <vault>/_graph/report.md
     --evidence "<ответ дословно>"`), затем снова `graph_check`.
4. Гейт: `graph_status` → `run.commands.gate`, затем `run.commands.close`.

Удалять плоские спеки — решение пользователя после приёмки; сам их не удаляй и не предлагай удалить файл,
перенесённый не полностью.

## Диагностика — `/forge-graph diag`

`graph_diag` пишет пакет `_graph/diag/diag-<дата>-<KEY>.md`: версии, окружение, прогоны, здоровье графа,
где буксовала модель, правила. Текста спеки в нём нет; самопроверка утечки — до записи (отказ
`E-diag-leak` — пакет не записан, назови пользователю номера строк). Пакет пишется и сам: в конце
`graph_check` и при каждой остановке гейта. Пользователь выносит его разработчикам.

## Режим вопросов — граф как источник ответов

Вопрос о спеке («кто закрывает задачу X», «что сломается, если поменять эндпойнт Y») — отвечай
инструментами обхода, а не чтением файлов заметок: один вызов, короткая выдача, `[[ссылки]]` ведут
пользователя в Obsidian. Работают на любом шаге и вне конвейера.

| вопрос | инструмент |
|---|---|
| найти узел по части имени, алиасу или ключу (`task:KOMPLEKT`, `http:GET /api/v1/tasks`) | `graph_find` |
| что это за узел, его связи; карточка, текст спеки, основания связей | `graph_node` (`body`: card / source / evidence) |
| кто вызывает, кто закрывает, что читает; соседи до 3 шагов | `graph_neighbors` (`edges` — ключ свойства, например `closed_by`; `dir`) |
| как связаны A и B; путь операции от UI до сервисов | `graph_path` |
| что затронет изменение эндпойнта, топика, данных, шедулера | `graph_impact` |
| с какими сервисами связан сервис и через что | `graph_service_links` |

Шаг пути подписан ключом свойства: `closed_by` — шаг против ребра `closes_task`. Нет узла — инструмент
вернёт похожие имена; уточни через `graph_find`. Поиск по прозе (grep) — только когда нет ни имени, ни
ключа.

## Чего не делать

- Не писать заметки vault и `.spec-graph/` руками — только инструментами `graph_*`.
- Не закрывать шаг словами: закрывает только гейт.
- Не угадывать корни спеки, исключения и путь vault — спрашивать.
